# 기획서 규칙

위키의 결정으로 공용 기획서를 만들고 갱신할 때 따른다. 공통 규칙은 [`AGENTS.md`](../AGENTS.md)에 있다. 이유와 검토한 대안은 [`docs/proposal.md`](../docs/proposal.md)에 있다.

## 파일

| 파일 | 내용 | 형식 |
| --- | --- | --- |
| `proposal/project-proposal.md` | 기획서. 팀 전체가 읽고, Android 레포가 sdd-android로 가져간다 | [`templates/proposal.md`](../templates/proposal.md) |
| `proposal/sources.yml` | 기획서 항목과 근거(결정, 미결)의 대응표 | [`templates/proposal-sources.yml`](../templates/proposal-sources.yml) |

- 두 파일은 이 규칙으로만 고친다. 기획서를 손으로 고치지 않는다. 뜻이 바뀌는 내용은 먼저 ingest로 위키에 넣고 기획서를 갱신한다.
- 두 파일은 같은 PR에서 함께 고친다. 대응표의 `version`은 기획서의 `version`과 같다.
- 기획서는 위키에 ingest하지 않는다([입력](ingest.md#입력)).

## 근거

| 위키 | 기획서 |
| --- | --- |
| `status: decided`, `kind: product` 결정 | 본문. 모든 결정이 대응표 어딘가에 있어야 한다 |
| `kind: product`, `status: open` 미결 항목 | 해당 항목의 `TBD:`. 항목이 없으면 3장의 맞는 묶음 아래, 첫 항목 앞에 둔다(대응표 `"*"`) |
| [용어집](../wiki/glossary.md)의 기획 용어와 동의어 | 1장 용어. 코드 심볼명은 옮기지 않는다 |
| 이관 기준선(`raw/baseline/`) | 첫 기획서(1.0.0)의 1장 서술에만 참고한다. 대응표 `"*"`에 경로를 남긴다. 그 뒤로는 읽지 않는다 |

- `superseded` 결정, `tech` 결정, 플랫폼 간 API 계약은 쓰지 않는다. API 형식과 엔드포인트도 쓰지 않는다.
- 결정에 없는 정책은 지어내지 않는다. 정해지지 않은 것은 `TBD:`로 남긴다.
- 화면 정의(치수, 색 값, 간격)는 쓰지 않는다. Figma가 기준이다([진실의 기준](../AGENTS.md#진실의-기준)). UI 용어에는 상태 목록과 정책 수치(개수 제한, 만료 기간 등)만 쓴다.

## 본문 작성

형식은 [`templates/proposal.md`](../templates/proposal.md)를 따른다. 템플릿의 주석은 작성 안내이고 기획서에 옮기지 않는다.

- 항목 ID는 `대문자 1~5자-숫자 3자리`다. `SYS`는 여러 항목이 함께 쓰는 공통 기능, `SCR`은 화면 단위 기능이다.
  - 한 번 준 ID는 바꾸지 않는다. 지운 항목의 번호는 다시 쓰지 않는다. 새 번호는 그 접두사의 지금까지 가장 큰 번호 다음이다(지운 항목 포함, 개정 기록에서 찾는다).
  - 2장 목표와 3장 항목은 ID가 하나씩 대응한다.
- 3장의 항목 묶음은 도메인이다. 묶음 제목은 도메인을 기획 용어(한국어)로 쓰고 순서는 [`domains.yml`](../domains.yml)을 따른다. 항목은 근거 결정의 주된 도메인 묶음에 둔다.
- 개발 용어(심볼명, 경로, API 이름, 코드 표기)를 쓰지 않는다. 결정에 심볼명이 나오면 용어집의 기획 용어로 바꾸고, 용어집에 없으면 풀어 쓴다. 풀어 쓴 용어는 "용어집에 없는 용어"로 변경 요약과 PR 본문에 남긴다. 용어집에 넣는 것은 ingest가 한다.
- 백틱(`` ` ``)을 쓰지 않는다. 형식 검사가 막는다.
- 4장 참고 자료에는 위키 레포와 결정에 나온 Figma 링크만 둔다. 결정별 출처는 대응표가 맡는다.

## 대응표

```yaml
version: 1.2.0
items:
  "*":
    - raw/baseline/2026-11-06-mvp-기획서.md
    - wiki/decisions/2026-10-01-오프라인-우선.md
  SCR-003:
    - wiki/decisions/2026-10-02-초대-링크-만료.md
    - wiki/open-questions/meetings/2026-11-10-초대.md
```

- 키는 기획서 항목 ID다. 항목 밖(1장 개요·원칙·용어, 2장 비목표, 3장 묶음 아래 항목 밖의 `TBD:`, 항목을 가로지르는 규칙)은 `"*"`다.
- 값은 그 부분의 근거 경로 목록이다. `wiki/decisions/`의 `product` 결정, `wiki/open-questions/` 파일, `"*"` 아래의 `raw/baseline/` 파일만 쓴다.
- 결정 하나가 여러 항목에 들어가면 각 항목에 모두 적는다.
- 항목을 지우면 그 키도 지운다. 지운 항목의 결정이 비목표로 옮겨 가면 `"*"`로 옮긴다.

## 개정 등급

항목마다 등급을 매긴다. 기준은 그 변경 때문에 다른 직군(디자인, 서버, Android, iOS, QA)이 할 일이 어떻게 바뀌는지다.

| 등급 | 기준 | 예 |
| --- | --- | --- |
| `major` | 다른 직군이 이미 끝낸 작업을 다시 해야 한다 | 핵심 플로우나 IA 변경, 기능 삭제, 정책 반전, 정책 수치 변경, 데이터 구조나 API에 영향, 범위 재정의 |
| `minor` | 기존 작업은 유지되고 할 일만 늘어난다 | 신규 화면이나 기능 추가, 예외 케이스 추가, 옵션이나 상태값 추가, `TBD:` 확정, 새 `TBD:`, 빠졌던 동작 추가 |
| `patch` | 할 일이 바뀌지 않는다 | 오탈자, 문구 명확화, 서식이나 용어 통일 |

- 새 항목은 `minor` 이상, 지운 항목은 `major`다.
- 항목 밖(`"*"`)이 바뀌면 `"*"`에도 등급을 매긴다. 항목을 더하거나 지워 목록만 바뀐 것은 `"*"`의 `patch`다.
- 문서 버전은 그 개정에서 가장 큰 등급 하나만 올린다. 상위 자리가 오르면 하위 자리는 0이 된다(1.2.1 → 1.3.0 → 2.0.0).
- 첫 기획서는 `1.0.0`이고, 처음부터 위 기준을 그대로 적용한다. MVP까지 구현된 이관 기준선에서 뽑기 때문이다. `0.x.x`는 쓰지 않는다.
- 위키 결정 없이 고칠 수 있는 것은 `patch`뿐이다. 뜻이 바뀌면 멈추고 ingest를 먼저 하라고 알린다.

**위키 변화와 기획서**

| 위키의 변화 | 기획서 | 등급 |
| --- | --- | --- |
| 새 결정, 기존 항목에 없는 기능 | 새 항목 | `minor` |
| 새 결정, 기존 항목에 동작이 늘어남 | 항목 수정 | `minor` |
| 미결 해소(`TBD:` 확정) | 항목 수정 | `minor` |
| 새 미결 | `TBD:` 추가 | `minor` |
| 대체 결정이 동작, 정책, 수치, 플로우를 바꿈 | 항목 수정 | `major` |
| 대체 결정이지만 할 일이 같음 | 항목 수정 | `patch` |
| 대체 결정이 기능을 범위에서 뺌 | 항목 삭제, 비목표로 옮김 | `major` |
| 미결이 결정 없이 `dropped` | `TBD:` 삭제 | 할 일에 따라 |
| 용어집 변경 | 1장 용어(`"*"`) | 할 일에 따라 |

표는 판단을 돕는 예다. 등급은 위 기준으로 정하고, 표와 다르게 매기면 이유를 적는다.

## 흐름

1. 위키 clone(`~/gguk/gguk-wiki`)이 default 브랜치이고 커밋하지 않은 변경이 없는지 확인한다. 처리는 [ingest 흐름](ingest.md#흐름) 1과 같다.
2. default 브랜치를 최신으로 맞추고 작업 브랜치(`proposal/<날짜>`)를 만든다.
3. 기획서, 대응표, 결정, 미결, 용어집을 읽고 반영할 변화를 찾는다.
   - 대응표에 없는 `decided` `product` 결정
   - 대응표의 결정 중 `superseded`가 된 것. `superseded_by`를 따라 지금 유효한 결정을 찾는다
   - 대응표의 미결 중 `resolved`, `dropped`가 된 항목. `resolved_by` 결정을 함께 읽는다
   - 대응표에 없는 `open` `product` 미결
   - 1장 용어와 다른 용어집의 기획 용어
   - 기획서가 없으면 첫 기획서를 만든다. 모든 `decided` `product` 결정과 `open` `product` 미결, 용어집, 이관 기준선을 읽는다.
4. 변화마다 고칠 항목(기존 항목, 새 항목, `"*"`)을 정하고 [개정 등급](#개정-등급)을 제안한다. 반영할 변화가 없으면 "반영할 내용 없음"을 알리고 작업 브랜치를 지운 뒤 끝낸다.
5. 실행한 사람에게 변경 요약을 보여 주고 확인받는다.
   - 항목마다 ID, 이름, 하는 일(추가, 수정, 삭제), 등급, 등급의 이유, 근거 결정 경로
   - 새 버전 번호
   - 용어집에 없는 용어
   - 실행한 사람이 바꾼 등급을 따른다. 항목을 지목하지 않은 답("진행" 등)은 제안한 등급을 승인한 것으로 본다.
6. 기획서 본문, frontmatter, 대응표를 고친다.
   - `version`을 올리고 `updated`를 오늘 날짜로 바꾼다.
   - `revisions` 끝에 `version`, `date`, `items`(항목 ID → 등급)를 더한다. `items`에는 본문이 바뀐 항목과 `"*"`를 빠짐없이 적는다. 기존 개정 기록은 고치지 않는다.
   - 첫 기획서는 `created`와 `updated`를 오늘 날짜로 하고, `revisions`에 `version: 1.0.0`과 `date`만 넣는다. 이전 버전이 없어 등급을 매길 대상이 없다(sdd-android가 문서를 완료할 때와 같다).
7. 커밋하고 `gh pr create`로 PR을 만든다. PR 본문은 흐름 5의 변경 요약이다. 팀은 PR 본문에서 바뀐 부분만 본다.
8. PR을 만든 뒤 `gh pr checks --watch`로 형식 검사(`check`) 결과를 확인한다. 실패하면 고쳐 같은 브랜치에 push한다. 통과하면 default 브랜치로 돌아간다. merge는 실행한 사람이 한다.

- 세션은 merge하지 않는다. 자기가 만든 브랜치와 PR만 다룬다.
- PR 없이 끝나면 자기가 만든 작업 브랜치를 지우고 default 브랜치로 돌아간다. 버릴 변경이 있으면 흐름 1의 stash 규칙을 따른다.
- Python이 있으면 PR을 만들기 전에 `python scripts/check.py --base origin/main`을 돌릴 수 있다. 가상 환경은 clone 밖에 둔다.
- 갱신 PR이 열려 있는 동안 다른 갱신을 시작하지 않는다. `gh pr list --state open --json number,title,files`로 `proposal/`을 고친 열린 PR을 찾고, 있으면 그 PR이 merge된 뒤 진행한다. 두 PR이 같은 버전을 쓰기 때문이다.
