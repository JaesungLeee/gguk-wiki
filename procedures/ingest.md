# Ingest 규칙

위키에 정보를 넣을 때 따른다. 공통 규칙은 [`AGENTS.md`](../AGENTS.md)에 있다.

## 파일 이름

- `YYYY-MM-DD-제목.md`로 한다. 제목은 한국어로 쓰고 단어 사이를 `-`로 잇는다.
  - `raw/`: 원본의 날짜(회의 날짜, 문서 최종 수정일, 받은 날). 이름이 규칙과 다른 파일(노션 내보내기 등)은 이름만 바꾸고 내용은 그대로 둔다.
  - `wiki/decisions/`: `decided_at`.
  - `wiki/action-items/`, `wiki/open-questions/`: 원본의 `raw/` 아래 경로를 그대로 따른다. 예: `raw/meetings/2026-11-10-결제-정책.md` → `wiki/open-questions/meetings/2026-11-10-결제-정책.md`
- `raw/`는 마크다운만 받는다. 노션 페이지와 STT 요약도 마크다운으로 저장한다.
- 기획 문서가 고쳐지면 기존 파일을 바꾸지 않고 새 파일로 다시 넣는다.

## 공개 범위

위키 레포는 public이다. 올라간 내용은 지워도 커밋 이력, fork, 검색 엔진 캐시에 남으므로 넣기 전에 거른다.

| 구분 | 대상 |
| --- | --- |
| 허용 | 팀원 목록(`people.yml`)에 있는 사람의 이름·GitHub 아이디·직무, Figma 링크 |
| 금지 | 연락처(전화번호, 이메일 등), 인사·평가·급여 정보, 특정인을 알아볼 수 있는 개인 사정(건강, 가족, 거취 등), 비밀값(API 키, 토큰, `.env` 내용, 키 파일) |

팀원 목록에 없는 사람(외부 인원, 목록에 추가하지 않은 팀원)의 이름은 위키 어디에도 남기지 않는다. 원본에 있으면 [인물](#인물)대로 "알 수 없음"으로 바꿔 저장한다. 금지 항목과 달리 멈추지 않는다.

원본에 금지 항목이 있으면 PR을 만들지 않고 멈춘다. 지울 부분의 위치와 종류를 알려 주고, 업로더가 원본(파일, 노션 페이지, 채팅 메시지)을 고친 뒤 다시 넣게 한다. 업로더가 빼고 진행하라고 해도 세션은 원본을 고치지 않는다.

- 차단 안내에는 금지 값을 다시 적지 않는다. 위치와 종류만 적는다.
- 표에 딱 맞지 않지만 민감해 보이는 내용은 "공개 범위 확인 필요"로 위치와 종류만 보여 주고 묻는다. 업로더가 괜찮다고 하면 넣고, 아니라고 하거나 답이 없으면 금지 항목처럼 멈춘다.
- 노션 MCP 본문의 사람 멘션은 예외로 이름으로 바꿔 저장하고, 페이지 속성의 Alt 공유 URL은 값을 비워 저장한다([노션 회의록](#입력)).
- 검사 결과는 변경 요약과 PR 본문에 한 줄로 남긴다. 예: "공개 범위: 금지 항목 없음"

## 도메인

- `domains` 값은 [`domains.yml`](../domains.yml)의 `name`에서 고른다. 결정과 미결 항목은 1개 이상 필수, 액션 아이템과 채팅 원본은 선택이다.
- 분류 규칙
  1. 데이터 규칙은 엔티티 도메인에, 순서와 시점은 흐름 도메인(`onboarding`, `share-intake`)에 넣는다.
  2. 여러 도메인에 걸치면 모두 단다. 예: 초대 합류가 끝나면 멤버 전원에게 푸시 → `[invitation, notification]`
  3. 특정 화면에 속한 디자인 결정은 그 화면의 도메인에 넣는다. `design-system`은 화면·엔티티에 속하지 않는 디자인 결정(글자, 색 체계, 공통 컴포넌트, 접근성)만 받는다. 예: 지도 클러스터 표시 → `place`
- 맞는 도메인이 없을 때만 `domains.yml`을 고친다. 기존 도메인 여러 개를 다는 것으로 충분하면 고치지 않는다.
  - 새 도메인은 기존 도메인 어디에도 속하지 않는 새 엔티티나 여러 엔티티에 걸친 새 흐름에만 만든다. 예: 결제 정책 → `payment`. 이름은 영어 소문자와 하이픈으로 쓴다. 예: `share-intake`
  - 새 흐름 도메인을 추가하면 분류 규칙 1의 흐름 도메인 목록도 고친다.
  - 기존 엔티티의 새 측면이면 새 도메인을 만들지 않고 그 도메인의 `scope`를 보강한다. 예: 방 배경 이미지 → `room`의 `scope`에 "방 꾸미기"를 더한다.
- `domains.yml` 변경은 "도메인 추가 후보"나 "scope 보강 후보"로 보여 주고, 업로더가 확인한 것만 넣는다. 거절하면 기존 도메인에 넣는다.
  - 후보에는 이름과 `scope`(보강이면 고친 `scope`), 기존 도메인으로 안 되는 이유를 적는다.
  - 후보를 보여 주기 전에 위키 clone에서 `gh pr list --state open --json number,title,files`로 `domains.yml`을 고친 열린 PR을 찾는다. 비슷한 도메인을 추가하거나 같은 `scope`를 고치는 PR이 있으면 업로더에게 알리고, 그 PR이 merge된 뒤 작업 브랜치를 default 브랜치에 rebase해 이어 간다.
  - 확인한 변경은 ingest PR에 함께 넣는다.
- 도메인 이름을 바꾸거나 지울 때는 같은 PR에서 기존 문서의 `domains`도 고친다.

## 인물

위키에 남기는 사람 이름은 [`people.yml`](../people.yml)의 `name`뿐이다. 목록에 없는 사람은 "알 수 없음"으로 적는다.

- 사람을 가리키는 표기를 목록과 맞춘다. GitHub 아이디나 원본의 다른 표기로 적지 않는다.
  - 업로더 본인의 말(남의 말을 전달한다는 표시가 없으면): `gh api user --jq .login`의 아이디를 `github`에서 찾는다.
  - 남의 말·원본의 이름: 표기가 `name`이나 이름 부분(성을 뺀 것)과 같은 사람이 하나뿐이면 그 `name`을 쓴다. 여러 사람에 걸리면 추측하지 않고 묻는다.
  - 남의 말을 전한 것인지 모를 때만 묻는다.
- 목록에 없는 사람이면 "인물 추가 후보"로 보여 준다.
  - 팀원인지 외부 인원인지와 직무를 이 확인 항목 하나로 묻는다. 후보에는 아는 값만 적는다. `role`을 모르면 짐작하지 않고 비워 둔 채 묻는다. `github`는 업로더 본인이면 `gh api user`의 아이디, 남이면 업로더가 알려 준 값만 적는다. 이름과 아이디를 짝지어 추론하지 않는다.
  - 업로더가 추가를 확인하면 `people.yml`에 넣고 그 `name`을 쓴다. 확인한 변경은 ingest PR에 함께 넣는다.
  - 외부 인원이거나, 추가하지 않거나, 답이 없으면 "알 수 없음"으로 적는다. 외부 인원은 `people.yml`에 넣지 않는다.
  - 후보를 보여 주기 전에 `people.yml`을 고친 열린 PR을 [도메인](#도메인)과 같은 방법으로 찾는다. 같은 사람을 추가하는 PR이 있으면 업로더에게 알리고, 그 PR이 merge된 뒤 작업 브랜치를 default 브랜치에 rebase해 이어 간다.
  - 업로더 본인이 목록에 없으면 이름과 직무를 묻는다. 이름 답이 없으면 멈춘다.
- "알 수 없음"으로 적은 사람의 이름은 원본 본문에서도 "알 수 없음"으로 바꿔 저장한다. 바꾼 곳의 수를 변경 요약과 PR 본문에 적고, 원래 이름은 적지 않는다.
- 채팅 원본의 `author`는 말한 사람 한 명의 `name`이나 "알 수 없음"이다.

## 입력

| 입력 | 예 | 원본 위치 |
| --- | --- | --- |
| 회의록 파일 | `ingest ~/Downloads/2026-11-10-결제-정책.md` | `raw/meetings/` |
| 노션 회의록 (MCP) | `ingest https://www.notion.so/<페이지>` | `raw/meetings/` |
| 노션 회의록 (내보내기) | `ingest ~/Downloads/notion-export/` (Markdown & CSV로 내보낸 md) | `raw/meetings/` |
| STT 요약 (Alt) | 요약 탭을 "Copy"로 복사해 붙여 넣는다 | `raw/meetings/` (파일로 만든다) |
| 기획 문서 (PRD, 스펙) | `ingest ~/Downloads/정산-기획.md` | `raw/specs/` |
| 채팅으로 말한 내용 | "환불 기한 7일로 확정됐어. 위키에 넣어줘" | `raw/notes/` (파일로 만든다) |

- 어떤 입력이든 원본을 `raw/`에 먼저 남긴 뒤 반영한다.
- 원본은 입력 경로에서 받은 내용(파일 내용, 노션 MCP 본문, 채팅 메시지)을 그대로 저장한다. 바꾸거나 더할 수 있는 것은 이 문서에 적힌 것뿐이다.
  - 파일 이름([파일 이름](#파일-이름))
  - 노션 MCP 본문의 `notion_url`·`fetched_at`과 사람 멘션
  - 노션 MCP 본문 페이지 속성의 Alt 공유 URL(값을 비운다)
  - 목록에 없는 사람의 이름("알 수 없음"으로 바꾼다, [인물](#인물))
  - 채팅 원본의 frontmatter, ingest 요청 문구, 업로더의 보충 답
- 기획 문서는 팀이 확정본으로 공유한 것만 넣고, 결정은 `decided`로 넣는다. 초안은 넣지 않는다.
- 채팅 입력은 받은 메시지를 그대로 적는다. 요약하거나 보충하지 않는다. "위키에 넣어줘" 같은 ingest 요청 문구만 뺀다. 남의 말을 전달받았으면 전달 맥락("민지가 ~래")까지 메시지 전체를 적는다. 형식은 [`templates/note.md`](../templates/note.md)를 따른다.
- 채팅 원본의 `author`는 [인물](#인물)을 따른다.
- 채팅 입력 뒤 업로더가 입력 내용을 보충한 답(어느 항목인지, 누가 언제 말했는지 등)은 같은 `raw/notes/` 파일에 받은 순서대로 이어 적는다. 확인 항목의 승인·거절은 PR 본문에만 남긴다.

**노션 회의록**

- MCP: `notion-search`로 찾고 `notion-fetch`로 읽는다. 노션 페이지를 만들거나 고치는 도구는 쓰지 않는다.
- MCP로 받은 본문은 그대로 저장하고, 맨 위 frontmatter에 `notion_url`과 `fetched_at`만 더한다.
- MCP 본문의 사람 멘션은 표시 이름 글자로 바꿔 저장한다. 목록에 없는 사람의 멘션은 "알 수 없음"으로 바꾼다. MCP가 멘션에 붙이는 이메일은 작성자가 쓴 내용이 아니므로 원본 수정이 아니라 형식 변환으로 본다. 업로더에게 묻지 않고 바꾸고, 바꾼 멘션 수를 변경 요약과 PR 본문에 적는다. 이메일 값은 적지 않는다.
- 페이지 속성에 Alt 공유 URL이 있으면 [STT 요약](#입력)처럼 그 URL로 전사를 읽어 결정을 대조한다. 전사는 `curl`로 받은 페이지에서 그 세션에서만 읽고, WebFetch는 쓰지 않는다. 전사에서 근거를 찾지 못한 항목은 "결정 여부 불명확"으로 표시한다.
- 그 속성 값은 비워 저장하고 PR 본문에도 URL을 적지 않는다. 멘션처럼 형식 변환으로 보고, 변경 요약과 PR 본문에는 비운 속성 이름만 적는다.
- 멘션 밖의 금지 항목은 [공개 범위](#공개-범위)대로 멈춘다.
- 내보내기: 페이지 속성(날짜 등)이 frontmatter가 아니라 제목 아래 `Key: Value` 줄로 나오므로, `date`와 `domains`는 추론한다.

**STT 요약 (Alt)**

- 요약만 `raw/meetings/`에 저장한다. 전사와 공유 URL은 저장하지 않고 PR 본문에도 적지 않는다. 공유 URL은 로그인 없이 열린다.
- 요약의 결정 사항은 후보로만 쓴다. 업로더가 공유 URL을 주면 전사와 대조하고, 전사에서 근거를 찾지 못한 항목은 "결정 여부 불명확"으로 표시한다.
- 전사는 `curl`로 받은 페이지에서 그 세션에서만 읽는다. WebFetch는 쓰지 않는다.
- 날짜는 페이지의 공유 날짜를 쓰고 "추론함"으로 표시한다.

**플랫폼 레포의 ADR**

- ADR에서는 "무엇을 보여 주나"(동작, 화면 규칙, 플랫폼 간 계약)만 넣는다. "어떻게 구현하나"(모듈 구조, 라이브러리, 빌드, 개발 프로세스)는 넣지 않는다.
- 팀이 확인한 뒤에만 결정으로 넣는다. `source`는 확인한 회의록(`raw/meetings/`)이나 채팅(`raw/notes/`)이고, ADR은 `## 배경`에 링크로 인용한다.
- 확인 전에는 관련 도메인의 미결로 넣는다. 원본은 미결을 제기한 채팅(`raw/notes/`)이다.

## 흐름

1. 위키 clone(`~/gguk/gguk-wiki`)이 default 브랜치이고 커밋하지 않은 변경이 없는지 확인한다.
   - 현재 브랜치가 default 브랜치가 아니면 다른 ingest가 진행 중일 수 있으므로 멈추고 알린다.
   - 커밋하지 않은 변경이 있으면 멈추고 알린다. 업로더가 치우라고 하면 바뀔 파일 목록을 보여 주고 확인받은 뒤 `git stash push -u -m "ingest: <날짜>"`로 치운다. 멈출 때 바뀔 파일 목록과 치우는 방법을 이미 보여 줬으면, 업로더가 그 뒤에 치우라고 한 답을 확인으로 본다. `git stash pop`으로 되돌릴 수 있다고 알린다. 변경을 버리는 명령(`git checkout --`, `git reset --hard`, `git clean`)은 쓰지 않는다.
2. 입력을 읽고 [공개 범위](#공개-범위), 이관 여부([기존 자료 이관](#기존-자료-이관) 절이 있는 동안), 같은 원본을 확인한다.
   - 같은 원본(같은 `notion_url`, 같은 파일)이 이미 `raw/`에 있으면 멈추고 알린다. 원본이 바뀌었으면 기존 파일을 고치지 않고 새 파일로 넣을지 묻는다([파일 이름](#파일-이름)). 답이 없으면 넣지 않는다.
3. default 브랜치를 최신으로 맞추고 작업 브랜치(`ingest/<날짜>-<제목>`)를 만든다.
4. 원본을 `raw/`에 추가한다.
5. 기존 결정과 미결을 검색해 중복·대체 후보와 미결 해소 후보를 찾는다([중복·충돌 확인](#중복충돌-확인)).
6. [반영 위치](#반영-위치)에 따라 위키를 수정하고, [용어집 반영](#용어집-반영) 후보를 찾는다.
7. 업로더에게 변경 요약과 [확인 항목](#업로더-확인-항목)을 보여 준다. 업로더가 확인하면 `gh pr create`로 PR을 만든다. 확인 항목은 PR 본문에도 남긴다.
8. PR을 만든 뒤 `gh pr checks --watch`로 형식 검사(`check`) 결과를 확인한다. 실패하면 고쳐 같은 브랜치에 push한다. 통과하면 default 브랜치로 돌아간다. merge는 업로더가 한다.

- 세션은 merge하지 않는다. 자기가 만든 브랜치와 PR만 다룬다.
- PR 없이 끝나면(업로더가 PR을 만들지 말라고 하는 등) 자기가 만든 작업 브랜치를 지우고 default 브랜치로 돌아간다. 버릴 변경이 있으면 흐름 1의 stash 규칙을 따른다.
- Python이 있으면 PR을 만들기 전에 `python scripts/check.py --base origin/main`을 돌릴 수 있다. 의존성(`scripts/requirements.txt`)을 설치할 가상 환경(venv)은 clone 밖에 둔다. clone 안에 두면 다음 ingest가 커밋하지 않은 변경으로 멈춘다.

## 반영 위치

| 원본의 내용 | 반영 위치 | 형식 |
| --- | --- | --- |
| 결정사항 | `wiki/decisions/` | [`templates/decision.md`](../templates/decision.md) |
| 액션 아이템 | `wiki/action-items/` | [`templates/action-items.md`](../templates/action-items.md) |
| 미결 사항 | `wiki/open-questions/`. 결정 문서로 만들지 않는다 | [`templates/open-questions.md`](../templates/open-questions.md) |
| 논의 내용 | 결정 문서의 `## 배경`, `## 검토한 대안`에만 인용 | — |

- 회의록이 아닌 기획 문서와 채팅 입력도 같은 기준으로 나눈다.
- 결정 문서는 내용이 정해진 것만 만든다. 결정 문장 안의 정해지지 않은 부분(예: "방식은 다음 회의에서 정한다")은 `## 결정`에 쓰지 않고 미결로 나눈다.
- 같은 원본 안의 같은 미결은 한 항목으로 합친다. 기존 `open` 미결과 같으면 "미결 중복 후보"로 보여 준다.
- 결정의 `platforms`는 1개 이상 적는다. 하지 않기로 한 결정(비목표, 스펙 아웃)은 그 기능을 만들 수 있었던 직무를 모두 적는다. 예: 계정 탈퇴를 MVP에서 다루지 않음 → `[server, android, ios, design]`
- 결정 문서 본문의 다섯 섹션은 모두 둔다. 원본에 내용이 없으면 "원본에 없음"이라고 적는다.
- 값이 없는 선택 필드는 줄을 뺀다.
- 액션 아이템의 담당자(`assignee`)는 맡은 사람의 목록이다. 한 명이어도 목록으로 쓰고, 원소는 `people.yml`의 `name`, "알 수 없음", "미정" 중 하나다. GitHub 아이디나 팀 이름은 쓰지 않는다.
  - 사람: [인물](#인물)대로 `name`을 쓴다. 목록에 없으면 "인물 추가 후보"를 거쳐, 추가하지 않으면 "알 수 없음"으로 쓴다.
  - 팀: "디자인 팀", "안드로이드 팀"처럼 직무로 부르면 `people.yml`에서 그 `role`의 팀원 전원으로 펼친다. "모두", "전체"는 목록의 모든 팀원이다. 직무로 맞출 수 없는 팀 표기는 업로더에게 묻는다.
  - 여러 표기가 같은 사람을 가리키면 한 번만 쓴다. 순서는 원본에 나온 순서이고, 팀을 펼친 사람은 `people.yml`의 순서를 따른다. 예: "재성, 디자인 팀" → `[이재성, 김민호, 이영]`
  - "미정": 팀원이 맡지만 누구인지 정해지지 않은 몫이다. 원본에 담당자가 없거나, 여러 사람에 걸리거나 맞출 수 없는 팀 표기인데 답이 없으면 그 몫을 "미정"으로 쓴다. 정해진 사람과 함께 올 수 있다. 예: `[이재성, 미정]`
- 채팅 원본의 "내가 할게"처럼 담당자가 1인칭이면 `author`로 채우지 않고 업로더에게 누구인지 묻는다. 답은 보충 답으로 `raw/notes/` 파일에 이어 적고, 위와 같이 `assignee`를 정한다. 답이 없으면 `[미정]`으로 쓴다.

**액션 아이템 완료**

- 회의록에 지난 액션 아이템의 완료가 적혀 있거나 채팅으로 완료를 알리면, 해당 항목의 `status`를 `done`으로 바꾼다.
- 채팅으로 알린 완료도 `raw/notes/`에 남긴다.
- 어느 항목인지 애매하면 추측하지 않고 업로더에게 묻는다.

**미결 해소**

- 새 결정이 기존 미결을 푸는 것으로 보이면 "미결 해소 후보"로 보여 준다.
- 업로더가 확인한 것만 해당 항목을 `status: resolved`로 바꾸고 `resolved_by`에 결정 경로를 적는다.
- 결정 없이 더 다루지 않기로 했으면 `dropped`로 바꾼다.

반영할 내용이 없으면 업로더에게 "반영할 내용 없음"을 알리고, 원본만 담은 PR을 만든다.

## 결정 대체

- 결정이 바뀌면 기존 파일을 고치거나 지우지 않는다. 새 결정 파일을 만들고 `supersedes`로 이전 결정을 가리킨다.
- 같은 PR에서 이전 결정의 `status`를 `superseded`로 바꾸고 `superseded_by`를 채운다.
- 결정 하나가 여러 결정을 대체하면 `supersedes`에 이전 결정을 목록으로 모두 적고, 이전 결정마다 `status`와 `superseded_by`를 바꾼다.
- 결정 하나를 여러 결정으로 나눠 대체하지 않는다. 이전 결정의 일부만 바뀌면 유지되는 내용까지 새 결정 하나에 다시 적고 이전 결정 전체를 대체한다. 유지되는 내용의 출처(이전 결정)는 `## 배경`에 밝힌다.
- 기존 결정 파일을 고칠 수 있는 예외는 이 대체 표시와, 도메인 이름 변경·삭제에 따른 `domains` 수정뿐이다.
- 대체 관계는 업로더가 확인한 것만 건다. 추론해서 자동으로 연결하지 않는다.
- 업로더가 대체를 확인하기 전에는 작업 트리에서도 이전 결정 파일을 고치지 않는다. 대체했을 때의 모습은 변경 요약에 글로만 보여 준다.

## 자유 형식 회의록

- 형식과 관계없이 회의록을 읽는다. [`templates/meeting.md`](../templates/meeting.md)는 권장 형식이다.
- 결정인지 논의인지 애매한 항목은 추측하지 않고 "결정 여부 불명확"으로 표시해 업로더에게 묻는다.
- frontmatter의 `date`나 `domains`가 없으면 추론한다. 날짜는 파일명이나 입력 시각에서, 도메인은 내용에서 찾고 "추론함"으로 표시한다.
- 템플릿을 지키지 않은 회의록도 거절하지 않는다. 대신 "결정사항 섹션이 없어 추출 정확도가 낮을 수 있습니다"처럼 경고한다.

## 중복·충돌 확인

- PR을 만들기 전에 기존 결정을 검색한다. 비슷한 결정이 있으면 "중복 또는 대체 후보"로 표시한다.
- 기획 문서의 결정이 기존 디자인 결정과 다를 때도 같다.
- 새 결정이 기존 결정의 `## 검토한 대안`에서 탈락한 안을 채택하면 별개로 보지 않고 "중복 또는 대체 후보"로 표시한다.
- 대체 후보를 보여 줄 때 같은 전제의 다른 `decided` 결정도 함께 보여 준다. 대체 후보 결정의 `## 결정`이 정한 규칙을 인용하거나 그 규칙에 기대는 다른 `decided` 결정이다. 결정마다 기대는 규칙을 한 줄로 밝힌다.
- 대체 여부는 업로더가 정한다. 어느 쪽도 자동으로 고치지 않는다.

## 용어집 반영

[`wiki/glossary.md`](../wiki/glossary.md)는 결정을 반영할 때 함께 채운다. 직역으로 코드에서 찾을 수 없는 용어만 적는다.

1. 반영할 결정에서 용어집에 없는 기획 용어를 뽑는다.
2. 영어 직역과 동의어로 코드 레포 3개의 default 브랜치에서 정의문을 찾는다.
   ```bash
   git -C ~/gguk/Team-MINO-Node grep -n -I -i -E \
     '(class|interface|object|struct|enum|protocol|fun|func|function)[[:space:]]+[[:alnum:]_]*refund' origin/HEAD
   ```
3. 찾은 이름이 직역과 다르거나 플랫폼마다 다르면, 근거 위치와 함께 "용어집 후보"로 보여 준다. 직역으로 찾히면 넣지 않는다.
4. 업로더가 확인한 것만 넣는다. 코드에서 찾지 못하면(아직 구현 전) 넣지 않는다.
5. 이미 용어집에 있는 용어를 다시 다루면 그 심볼을 다시 찾는다. 찾지 못하면 "용어집 갱신 후보"로 보여 준다.

- 용어집 칸에는 심볼명만 적는다. 경로와 주석(`([SYS-002]형)` 같은 것)은 넣지 않는다. 경로는 근거로만 보여 준다.
- 기획 용어 가나다순 위치에 넣는다.
- 채팅으로 알려 준 매핑("보관함은 iOS에서 Archive야")도 다른 채팅 입력처럼 `raw/notes/`에 남기고 반영한다.

## 반영하지 않는 것

- 코드나 git 이력으로 확인할 수 있는 사실. 용어집은 예외다.
- 오탈자, 서식 수정
- 원본에 없는 추측이나 보충 설명

## 업로더 확인 항목

| 표시 | 뜻 | 답이 없으면 |
| --- | --- | --- |
| 결정 여부 불명확 | 결정인지 논의인지 애매하다 | 결정이나 미결로 넣지 않고 PR 본문에만 남긴다 |
| 추론함 | 날짜, 도메인 등을 원본에서 직접 찾지 못해 추론했다 | 추론값을 쓴다 |
| 중복 또는 대체 후보 | 비슷한 기존 결정이 있다 | 대체하지 않는다 |
| 미결 중복 후보 | 같은 기존 `open` 미결이 있다 | 합치지 않고 따로 넣는다 |
| 미결 해소 후보 | 기존 미결을 푸는 결정으로 보인다 | 연결하지 않는다 |
| 용어집 후보 | 직역과 다른 코드 심볼을 찾았다 | 넣지 않는다 |
| 용어집 갱신 후보 | 용어집의 심볼을 코드에서 찾지 못했다 | 고치지 않는다 |
| 도메인 추가 후보 | 맞는 도메인이 없어 `domains.yml`에 새 도메인을 넣으려 한다 | 추가하지 않고 기존 도메인에 넣는다 |
| scope 보강 후보 | 기존 도메인의 `scope`를 넓혀 넣으려 한다 | 고치지 않고 기존 도메인에 넣는다 |
| 인물 추가 후보 | 목록에 없는 사람이라 `people.yml`에 넣으려 한다 | 추가하지 않고 "알 수 없음"으로 적는다(원본 본문 포함) |

- 확인 항목은 항목마다 "답이 없으면"의 처리를 함께 보여 준다.
- 항목을 지목하지 않은 답("진행" 등)은 모든 항목의 "답이 없으면" 처리를 승인한 것으로 본다.
- 업로더의 지시를 넓혀 해석하지 않는다. 어느 항목에 대한 답인지 애매하거나 보여 준 항목 밖의 변경을 뜻하면 되묻는다.

## 기존 자료 이관

> 기존 자료 이관이 끝나면 이 절을 지운다.

MVP 개발 중에 쌓인 자료를 한 번 옮긴다. PRD·스펙으로 현재 정책의 기준선을 만들고, 노션 회의록으로 배경을 보충한다.

- 이관 PR에서는 `domains.yml`을 고치지 않는다. 맞는 도메인이 없으면 그 원본의 이관을 멈추고 업로더에게 알린다. `domains.yml`을 고치는 PR을 먼저 merge한 뒤 이어 간다.
- 이 절이 있는 동안 회의록 입력에 이관 보충인지 적혀 있지 않으면 [흐름](#흐름) 2에서 멈추고 업로더에게 묻는다. 회의 날짜와 관련 기준선 문서의 날짜를 함께 보여 준다.
  - 이 질문은 필수 질문이다. 확인 항목 표 밖의 질문이라 "진행" 같은 지목 없는 답으로 대신하지 않는다. 답이 없으면 진행하지 않고 `raw/`에도 넣지 않는다.

1. **기준선**: PRD와 스펙 문서를 `raw/specs/`에 넣는다.
   - 원본 1건을 PR 1개로 만든다. 결정이 많으면 PR 본문을 도메인별로 묶는다.
   - 결정은 `decided`로 넣는다. `decided_at`은 원래 결정 날짜를 알면 그 날짜, 모르면 문서 날짜를 쓰고 "추론함"으로 표시한다.
   - 파일 이름의 날짜는 문서의 최종 수정일로 한다. 모르면 ingest한 날짜로 하고 "추론함"으로 표시한다.
   - PRD와 스펙이 서로 다르면 "중복 또는 대체 후보"로 표시하고 업로더가 정한다. 코드와 다르면 [진실의 기준](../AGENTS.md#진실의-기준)을 따른다.
   - PR 본문에 코드와 다른 곳을 "코드와 다른 곳: 없음", "코드와 다른 곳: N건", "코드와 다른 곳: 대조 안 함" 중 하나로 반드시 적는다.
2. **보충**: 자주 묻는 영역의 노션 회의록만 골라 `raw/meetings/`에 넣는다.
   - 기준선 결정을 대체하지 않는다. [결정 대체](#결정-대체)의 예외로, 관련 기준선 결정의 `## 배경`이나 `## 검토한 대안`에만 인용을 더한다. frontmatter와 `## 결정`은 고치지 않는다. 기준선과 다른 과거 결정도 같다.
   - 같은 도메인이면 한 PR에 여러 회의록을 넣을 수 있다.
   - 액션 아이템과 미결 사항은 넣지 않는다. 아직 유효한 것은 이후 회의록이나 채팅으로 새로 넣는다.
