위키를 무엇에 쓰고, 위키·기획서·디자인·플랫폼 문서를 어떤 순서로 만드는지 적는다. 위키에 넣고 조회하는 규칙은 [`AGENTS.md`](../AGENTS.md)와 [`procedures/`](../procedures/)가 정본이다.

## 배경

- 문서 구조는 Figma ← 기획서 ← 스펙 문서였다. 디자인이 기준이고, 기획서는 디자인에서, 스펙 문서는 기획서에서 뽑았다.
- 지금은 셋이 서로 맞지 않는다. Figma와 기획서가 어긋나면서 스펙 문서까지 어긋났다.
- 그래서 플랫폼 구현도 갈렸다. Android와 iOS의 구현이 다른 곳이 확인한 것만 7~8건이다. Android는 기획서대로 구현했고, iOS는 문서를 중간부터 받았다.
- 플랫폼마다 개발 위주 PRD를 따로 두면서 파편화가 심해졌다. Node PRD에는 지금 구현과 다른 `device_id` 내용과 기획 내용이 섞여 있다([미결 사항](README.md#미결-사항) 4).
- 지금 공유한 QA 시트는 그대로 쓸 수 없다.

## 위키의 목적

팀 전체가 같은 기획·의사결정 정보를 보게 한다.

- 위키에는 팀의 기획과 전체 의사결정, 두 플랫폼 이상(server, android, ios)이 함께 지켜야 하는 계약과 기술 결정을 둔다.
- 기획 결정과 기술 결정은 `kind`로 나눈다([결정 종류](../procedures/ingest.md#결정-종류)). 기획서와 기획·디자인 질문에는 기획 결정만 쓴다.
- 공용 기획서는 하나만 만들어 공유한다.
- 한 플랫폼 안에서만 영향이 있는 기술 결정은 각 레포에서 관리한다. 형식은 강제하지 않는다.
- 용어집은 코드 심볼명을 적는다. 조회가 기획 용어로 코드를 찾는 데 쓰는 표다.

계약과 기술 결정을 넣는 것은 API 리뷰처럼 플랫폼 간 합의를 정하는 회의도 위키에 들어와야 하기 때문이다. 결정과 그 회의의 액션 아이템이 근거와 함께 남고, 플랫폼 문서마다 합의가 다르게 굳는 일(Node PRD의 `device_id`)을 위키에서 먼저 잡을 수 있다.

| 검토한 안 | 판단 |
| --- | --- |
| 사용자에게 보이는 동작·정책만 넣고 계약은 서버 레포에 둔다 | 제외. 위키가 기획만 담아 단순하지만, API 리뷰 회의의 결정과 액션 아이템이 위키에 들어오지 못한다. 계약을 정한 이유와 이력이 레포마다 흩어진다 |
| **플랫폼 공통 계약·기술 결정도 넣고 `kind`로 나눈다** | 채택. 결정 형식과 검사에 `kind`가 늘지만, 기획서와 기획 질문은 `product`만 쓰면 된다 |

## 문서별 역할

| 문서 | 위치 | 내용 | 독자 |
| --- | --- | --- | --- |
| 위키 | `gguk-wiki` | 회의에서 정한 기획과 전체 의사결정, 플랫폼 공통 계약·기술 결정 | 팀 전체. 기술 결정은 각 파트 |
| 기획서 | 위키에서 뽑는다. 위키에 다시 넣지 않는다 | 유저 플로우, 정책, 기능 동작. 개발 용어를 쓰지 않는다 | 팀 전체 |
| 스펙 문서 | 스펙센터 | 기획서에서 뽑은 기능별 문서. 비기술적 내용. 위키에 넣지 않는다 | 팀 전체 |
| 화면 디자인 | Figma | 기획서를 바탕으로 한 화면 | 팀 전체 |
| 서버 API 명세 | `Team-MINO-Node`의 `docs/swagger.yaml` | 엔드포인트별 요청·응답. 위키의 계약 결정을 따른다 | 각 파트 |
| 플랫폼 기술 문서 | 각 코드 레포 | 그 플랫폼 안의 기술 결정. 기획 내용과 공통 계약은 빼고 현재 기획서와 위키 결정에 맞춘다 | 각 파트 |

**이름**

- 지금까지 "PRD"라고 부른 공용 문서는 "기획서"로 부른다. 독자가 개발자가 아니라 팀 전체이고, 개발 용어 없이 기획 내용만 담기 때문이다.
- 플랫폼 레포의 개발 위주 PRD(Node PRD 등)는 기획서가 아니라 플랫폼 기술 문서다. 기획 내용을 빼고 각 레포에서 관리한다.

| 검토한 안 | 판단 |
| --- | --- |
| 포괄적인 기획서와 각 파트 개발용 PRD를 함께 둔다 | 제외. 개발용 PRD 때문에 파편화가 심해졌다. 기획서를 개발자용 문서로 보면 기획 내용이 플랫폼마다 갈린다 |
| **기획서 하나만 공유하고, 플랫폼 내부 기술 결정은 각 레포에 둔다** | 채택. 위키와 레포의 목적이 나뉜다 |

## 흐름

**앞으로**

```text
회의 → 위키 → 기획서 → 디자인(Figma) → 각 파트 기술 문서
```

- 기획서가 디자인보다 먼저다. 디자인은 시각적으로만 표현해 스펙을 세세하게 정할 수 없고, 애매한 지점이 생긴다.
- 새 기능을 회의에서 논의하면 그 회의 내용을 위키에 넣고, 위키로 기획서를 업데이트한다.
- 기획서에서 바뀐 부분만 쉽게 볼 수 있게 한다.
- 기획서와 스펙 문서는 위키에 넣지 않는다(ingest 입력에서 뺀다). 위키에서 뽑는 문서라 넣으면 위키 내용이 다시 원본이 된다. 이관 기준선 기획서만 예외다([기존 자료 이관](ingest.md#기존-자료-이관)).
- 계약은 회의 → 위키(`tech` 결정) → 서버 API 명세 → 각 파트 기술 문서 순이다. 기획서에는 넣지 않는다.

| 검토한 안 | 판단 |
| --- | --- |
| 디자인 → 기획서(지금까지의 순서) | 제외. 논의된 내용으로 디자인을 먼저 만들고 Figma를 주고 기획서를 채웠다. 디자인이 정하지 않은 부분이 기획서에서 비거나 플랫폼마다 달라졌다 |
| **회의 → 위키 → 기획서 → 디자인** | 채택 |

**지금 (한 번만)**

이재성이 진행하고 단계마다 결과를 공유한다.

1. MVP까지 구현된 내용을 담은 기획서를 기준선으로, 지금까지의 회의 전사와 채팅 기록을 보충으로 위키에 옮긴다. 스펙 문서는 넣지 않는다([기존 자료 이관](ingest.md#기존-자료-이관)).
2. 위키로 기획서를 새로 뽑아 팀에 공유한다.
3. 각 파트는 기획서를 받아 플랫폼 문서에서 기획 내용을 빼고, 현재 기획서에 맞게 현행화한다.
4. QA에서 새 기획서에 맞춰 플랫폼 구현을 고친다.
