# Ingest (쓰기 경로)

위키에 정보가 반영되는 흐름을 정한다. 저장 형식은 [data-model.md](data-model.md)를 따른다.

## 입력

| 입력 | 예 | 원본 위치 |
| --- | --- | --- |
| 회의록 파일 | `ingest ~/Downloads/2026-11-10-결제-정책.md` | `raw/meetings/` |
| 노션 회의록 (MCP) | `ingest https://www.notion.so/<페이지>` | `raw/meetings/` |
| 노션 회의록 (내보내기) | `ingest ~/Downloads/notion-export/` (Markdown & CSV로 내보낸 md) | `raw/meetings/` |
| STT 요약 (Alt) | 요약 탭을 "Copy"로 복사해 붙여 넣는다 | `raw/meetings/` (스킬이 파일로 만든다) |
| 기획 문서 (PRD, 스펙) | `ingest ~/Downloads/정산-기획.md` | `raw/specs/` |
| 채팅으로 말한 내용 | "환불 기한 7일로 확정됐어. 위키에 넣어줘", "환불 API 기한 검증 끝났어" | `raw/notes/` (스킬이 파일로 만든다) |

- 어떤 입력이든 원본을 `raw/`에 먼저 남긴 뒤 반영한다. 모든 결정의 `source`가 원본을 가리키게 하기 위해서다.
- 기획 문서는 팀이 확정본으로 공유한 것만 넣는다([기존 자료 이관](#기존-자료-이관)).
- 채팅 입력은 받은 말을 그대로 적는다. 요약하거나 보충하지 않는다. 작성자는 말한 사람의 GitHub 아이디로 남긴다([`raw/notes/` 형식](data-model.md#위키-구조)).

**노션 회의록**

- MCP: `notion-search`로 찾고 `notion-fetch`로 읽는다. 노션 페이지를 만들거나 고치는 도구는 쓰지 않는다. 설정은 [필요 조건](plugin.md#필요-조건)을 따른다.
- MCP로 받은 본문(노션식 마크다운)은 그대로 저장하고, 맨 위 frontmatter에 `notion_url`과 `fetched_at`만 더한다.
- 내보내기: 페이지 속성(날짜 등)이 frontmatter가 아니라 제목 아래 `Key: Value` 줄로 나오므로, `date`와 `domains`는 추론한다([자유 형식 회의록 처리](#자유-형식-회의록-처리)). Windows에서는 경로가 길면 압축 해제가 실패하므로 짧은 경로에 푼다.

**STT 요약 (Alt)**

- 요약만 `raw/meetings/`에 저장한다. 전사와 공유 URL은 저장하지 않고 PR 본문에도 적지 않는다. 공유 URL은 로그인 없이 열리므로, public 레포에 남기면 전사 전체가 공개된다.
- 요약은 STT 도구의 AI가 만든 결과물이다. 요약의 결정 사항은 후보로만 쓰고, 업로더가 공유 URL을 함께 주면 전사와 대조한다. 전사에서 근거를 찾지 못한 항목은 "결정 여부 불명확"으로 표시한다.
- 전사는 `curl`로 받은 페이지에서 그 세션에서만 읽는다. WebFetch는 페이지를 작은 모델이 다시 요약해서 돌려주므로 쓰지 않는다.
- 페이지에는 공유 날짜만 있으므로 그 날짜를 쓰고 "추론함"으로 표시한다. 실제 회의 날짜와 다르면 업로더가 고친다.

## 흐름

각자 PC의 Claude Code에서 ingest 스킬로 실행한다. 개인 구독을 쓰고, 서버와 API 키는 쓰지 않는다. 필요한 도구는 [필요 조건](plugin.md#필요-조건)을 따른다.

1. 위키 clone(`~/gguk/gguk-wiki`, [작업 공간](plugin.md#작업-공간))을 default 브랜치 최신으로 맞추고 작업 브랜치(`ingest/<날짜>-<제목>`)를 만든다. clone에 커밋하지 않은 변경이 있으면 멈추고 알린다.
2. [공개 범위](data-model.md#공개-범위)를 검사한다. 금지 항목이 있으면 멈추고, 원본에서 지울 부분을 알려 준다.
3. 원본을 `raw/`에 추가한다.
4. 기존 결정을 검색해 중복·대체 후보를 찾는다([중복·충돌 확인](#중복충돌-확인)).
5. [섹션별 반영 위치](#섹션별-반영-위치)에 따라 위키를 수정하고, [용어집 반영](#용어집-반영) 후보를 찾는다.
6. 업로더에게 변경 요약과 확인 항목("결정 여부 불명확", "추론함", "중복 또는 대체 후보", "용어집 후보", "용어집 갱신 후보")을 보여 준다. 업로더가 확인하면 `gh pr create`로 PR을 만든다.
7. CI 형식 검사가 통과하면 업로더가 merge한다.

실행 모델은 [operations.md](operations.md)를 따른다.

## 승인 구조 (Ownership)

도메인별 담당자는 두지 않는다. 결정은 회의에서 이미 합의된 것이므로, 승인은 LLM이 결정을 빠뜨리거나 지어내지 않았는지 확인하는 단계다.

- 확인은 업로더가 PR을 만들기 전에 Claude Code에서 한다([흐름](#흐름) 6번). 내용을 가장 잘 아는 사람이기 때문이다.
- 다른 팀원의 승인은 요구하지 않는다. 업로더가 직접 merge한다. 결정 대체가 포함된 PR도 같다.
  - PR을 업로더 본인 계정으로 만들므로, GitHub에서는 자기 PR을 승인할 수 없다.
  - 다른 사람의 승인을 기다리게 하면 회의록마다 PR이 밀린다.
- 누가 확인했는지는 PR 작성자와 merge한 사람으로 남는다.
- 다른 팀원도 PR에 의견을 남기거나 merge할 수 있다.

## 자유 형식 회의록 처리

- ingest 스킬은 형식과 관계없이 회의록을 읽는다. [회의록 템플릿](data-model.md#회의록-템플릿)은 권장 형식이다.
- 결정인지 논의인지 애매한 항목은 추측하지 않고 "결정 여부 불명확"으로 표시해 업로더에게 묻는다. PR 본문에도 남긴다.
- frontmatter의 `date`나 `domains`가 없으면 추론한다. 날짜는 파일명이나 입력 시각에서, 도메인은 내용에서 찾고 "추론함"으로 표시한다.
- 템플릿을 지키지 않은 회의록도 거절하지 않는다. 대신 "결정사항 섹션이 없어 추출 정확도가 낮을 수 있습니다"처럼 경고한다.

## 섹션별 반영 위치

| 회의록 섹션 | 반영 위치 |
| --- | --- |
| 결정사항 | `wiki/decisions/` 결정 문서 + 관련 도메인 페이지 요약 |
| 액션 아이템 | `wiki/action-items/` 원본별 파일([액션 아이템 형식](data-model.md#액션-아이템-형식)) |
| 미결 사항 | 관련 도메인 페이지의 미결 목록. 결정 문서로 만들지 않는다 |
| 논의 내용 | 결정 문서의 배경·검토한 대안에만 인용 |

기획 문서와 채팅 입력도 같은 기준으로 결정, 액션 아이템, 미결 사항을 나눠 반영한다.

**액션 아이템 완료**

- 회의록에 지난 액션 아이템의 완료가 적혀 있거나, 채팅으로 완료를 알리면 해당 파일의 `status`를 `done`으로 바꾼다.
- 채팅으로 알린 완료도 다른 채팅 입력처럼 `raw/notes/`에 남긴다. 누가 언제 완료라고 했는지 기록하기 위해서다.
- 어느 항목인지 애매하면 추측하지 않고 업로더에게 묻는다.

**반영하지 않는 것**

- 코드나 git 이력으로 확인할 수 있는 사실. 용어집은 예외다([용어집 반영](#용어집-반영))
- 오탈자, 서식 수정
- 원본에 없는 추측이나 보충 설명

반영할 내용이 없으면 업로더에게 "반영할 내용 없음"을 알리고, 원본만 담은 PR을 만든다. 원본은 결정이 없어도 보관한다.

## 용어집 반영

[용어집](data-model.md#위키-구조)은 결정을 반영할 때 함께 채운다. 코드에서 확인한 심볼명이지만, 조회가 기획 용어로 코드를 찾으려면 매핑이 필요하므로 [반영하지 않는 것](#섹션별-반영-위치)의 예외로 둔다.

1. 반영할 결정에서 용어집에 없는 기획 용어를 뽑는다.
2. 영어 직역과 동의어로 코드 레포 3개의 default 브랜치에서 정의문을 찾는다.
   ```bash
   git -C ~/gguk/Team-MINO-Node grep -n -I -i -E \
     '(class|interface|object|struct|enum|protocol|fun|func|function)[[:space:]]+[[:alnum:]_]*refund' origin/HEAD
   ```
3. 찾은 이름이 직역과 다르거나 플랫폼마다 다르면, 근거 위치와 함께 "용어집 후보"로 보여 준다. 직역으로 찾히면 넣지 않는다. 경로는 근거로만 보여 주고 용어집에는 적지 않는다.
4. 업로더가 확인한 것만 넣는다. 코드에서 찾지 못하면(아직 구현 전) 넣지 않는다.
5. 이미 용어집에 있는 용어를 다시 다루면 그 심볼을 다시 찾는다. 찾지 못하면 "용어집 갱신 후보"로 보여 준다.

채팅으로 알려 준 매핑("보관함은 iOS에서 Archive야")도 다른 채팅 입력처럼 `raw/notes/`에 남기고 반영한다. [기존 자료 이관](#기존-자료-이관)에서는 기준선 PRD를 넣으면서 같은 절차로 채운다.

## 중복·충돌 확인

PR을 만들기 전에 기존 결정을 검색한다. 비슷한 결정이 있으면 "중복 또는 대체 후보"로 표시한다. 대체 여부는 업로더가 판단한다.

기획 문서의 결정이 기존 디자인 결정과 다를 때도 같다. PRD는 디자인에서 뽑은 문서라 둘이 어긋날 수 있다. 어느 쪽도 자동으로 고치지 않는다.

## 기존 자료 이관

MVP 개발 중에 쌓인 자료를 한 번 옮긴다. PRD·스펙으로 현재 정책의 기준선을 만들고, 노션 회의록으로 배경을 보충한다.

1. `AGENTS.md`에 도메인 목록을 먼저 고정한다. 목록에 없는 도메인은 쓸 수 없기 때문이다([도메인 목록 고정](data-model.md#위키-구조)).
2. **기준선**: PRD와 스펙 문서를 `raw/specs/`에 넣는다.
   - 원본 1건을 PR 1개로 만든다. 결정이 많으면 PR 본문을 도메인별로 묶는다.
   - MVP에 구현된 내용이므로 결정은 `decided`로 넣는다. `decided_at`은 원래 결정 날짜를 알면 그 날짜, 모르면 문서 날짜를 쓰고 "추론함"으로 표시한다.
   - 파일 이름의 날짜는 문서의 최종 수정일로 한다. 모르면 ingest한 날짜로 하고 "추론함"으로 표시한다.
   - PRD와 스펙이 서로 다르면 "중복 또는 대체 후보"로 표시하고 업로더가 정한다. 코드와 다르면 [진실의 기준](data-model.md#진실의-기준-source-of-truth)을 따른다.
3. **보충**: 자주 묻는 영역의 노션 회의록만 골라 `raw/meetings/`에 넣는다.
   - 기준선보다 앞선 회의록이므로 기준선 결정을 대체하지 않는다. 관련 기준선 결정의 `## 배경`이나 `## 검토한 대안`에 인용만 한다. 기준선과 다른 과거 결정도 같다.
   - 같은 도메인이면 한 PR에 여러 회의록을 넣을 수 있다.
   - 액션 아이템과 미결 사항은 넣지 않는다. MVP 시기의 항목이라 대부분 끝났거나 의미가 없고, 넣으면 `action-items.md`와 도메인 페이지 미결 목록에 낡은 항목이 쌓인다. 아직 유효한 것은 이후 회의록이나 채팅으로 새로 넣는다.

이관 뒤에 들어오는 기획 문서(phase 2 PRD 등)도 팀이 확정본으로 공유한 것만 넣고, 결정은 `decided`로 넣는다. GGUK에는 기획자가 따로 없다. 팀 아이디에이션에서 합의한 내용을 디자이너가 디자인으로 만들고, 그 디자인에서 PRD를 뽑는다. PRD는 이미 합의된 결정을 옮긴 문서라 따로 승인할 사람이 없다. 초안은 넣지 않는다. 초안 단계의 논의는 아이디에이션 회의록으로 들어온다.

## 인덱스 생성과 형식 검사

`scripts/`의 인덱스 생성과 형식 검사는 CI에서만 실행하므로 Python으로 쓴다. 개발자 PC에는 Python을 요구하지 않는다.

**인덱스는 스크립트가 만든다**

- `index.md`, `log.md`, `action-items.md`는 각 문서의 frontmatter로 스크립트가 생성한다. LLM과 사람 모두 직접 수정하지 않는다.
- main에 merge된 뒤 CI가 다시 생성해 커밋한다. 같은 입력이면 항상 같은 결과가 나와야 한다.
- 여러 ingest PR이 동시에 같은 파일을 고치면 merge 충돌이 반복되기 때문이다.
- `action-items.md`는 열린 항목을 기한순으로 정렬만 하고 "기한 지남"은 표시하지 않는다. 생성한 날짜에 따라 결과가 달라지기 때문이다. 기한이 지났는지는 조회할 때 판단한다([위키 조회](retrieval.md#위키-조회)).

**형식 검사는 PR에서 막는다**

CI에서 아래를 검사하고, 실패하면 merge를 막는다([main 보호 규칙](#main-보호-규칙)).

- 결정 문서의 필수 필드와 `status` 값
- 결정 문서의 `source`, `supersedes`, `superseded_by`가 가리키는 파일이 실제로 있는지
- 액션 아이템 파일의 필수 필드와 `status` 값, `source`가 가리키는 파일이 실제로 있는지
- `domains` 값이 고정된 도메인 목록에 있는지
- `raw/`의 기존 파일을 고치거나 지우지 않았는지
- `index.md`, `log.md`, `action-items.md`를 추가하거나 고치지 않았는지. PR에서 고친 내용은 merge 뒤 CI가 덮어써 조용히 사라지기 때문이다. 삭제는 허용한다. 생성 파일을 없앨 때 남은 파일을 지울 수 있어야 하고, 잘못 지워도 CI가 다시 만든다

형식 검사는 PR 쪽 코드로 실행되므로, 같은 PR에서 검사 스크립트를 고치면 피할 수 있다. LLM의 실수를 막는 장치이고 의도적인 우회는 막지 않는다.

## main 보호 규칙

위키 레포는 public이다. Free 플랜의 private 레포에서는 ruleset을 쓸 수 없어서 공개로 정했다. 공개에 따른 규칙은 [공개 범위](data-model.md#공개-범위)를 따른다.

- main은 ruleset으로 아래를 강제한다.
  - PR을 거쳐야 merge할 수 있다. 승인 수는 0명이다([승인 구조](#승인-구조-ownership)).
  - 형식 검사가 통과해야 merge할 수 있다.
  - force push와 브랜치 삭제를 막는다.
- ruleset은 두 번에 나눠 건다([다음 단계](README.md#로드맵)). 형식 검사 필수와 GitHub App 우회는 형식 검사 CI가 merge된 뒤에 추가한다. 필수 검사가 보고되지 않으면 PR이 "Waiting for status to be reported" 상태로 막히기 때문이다.
- PR 없이 main에 커밋하는 곳은 CI 하나뿐이다. CI는 GitHub App 토큰으로 `index.md`, `log.md`, `action-items.md`를 다시 만들어 커밋하고, 이 App만 ruleset 우회 대상으로 둔다. ruleset 우회 대상에는 GitHub App을 넣을 수 있다.
- ruleset은 우회 대상이 고칠 경로를 제한하지 못한다. 이 세 파일 밖을 고치지 않는 것은 CI 코드가 지킨다.
- App 토큰으로 만든 커밋은 워크플로를 다시 실행한다. 재생성 결과가 바뀌지 않으면 커밋하지 않으므로 한 번에 멈춘다.

**GitHub App과 비밀값**

| 항목 | 내용 |
| --- | --- |
| App 권한 | `gguk-wiki` Contents: Write |
| 비밀값 | `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`를 GitHub Actions secrets에 둔다 |
| 노출 방지 | 인덱스 재생성 워크플로는 main push에서만 실행한다. 외부 fork PR에는 secrets가 전달되지 않으므로, PR 형식 검사는 secrets 없이 돈다 |
