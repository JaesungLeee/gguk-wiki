# Ingest (쓰기 경로)

위키에 정보가 반영되는 흐름을 왜 그렇게 정했는지 적는다. 규칙의 정본은 [procedures/ingest.md](../procedures/ingest.md)이고, 저장 형식은 [data-model.md](data-model.md)를 따른다.

## 입력

규칙: [procedures/ingest.md 입력](../procedures/ingest.md#입력)

입력은 회의록 파일, 노션 회의록(MCP, 내보내기), STT 요약(Alt), 기획 문서, 채팅, 플랫폼 레포의 ADR이다.

- 어떤 입력이든 원본을 `raw/`에 먼저 남긴다. 모든 결정의 `source`가 원본을 가리키게 하기 위해서다.
- 기획 문서는 팀이 확정본으로 공유한 것만 넣는다([기존 자료 이관](#기존-자료-이관)).
- 채팅 입력은 요약하거나 보충하지 않는다. 원본이 LLM의 해석이 되면 `source`로서 의미가 없다.

**노션 회의록**

- MCP 설정은 [필요 조건](plugin.md#필요-조건)을 따른다. 노션 페이지를 만들거나 고치는 도구는 쓰지 않는다. 위키는 노션을 읽기만 한다.
- 내보내기는 페이지 속성이 frontmatter가 아니라 제목 아래 `Key: Value` 줄로 나오므로 `date`와 `domains`를 추론한다([자유 형식 회의록 처리](#자유-형식-회의록-처리)).

**STT 요약 (Alt)**

- 전사와 공유 URL은 저장하지 않는다. 공유 URL은 로그인 없이 열리므로, public 레포에 남기면 전사 전체가 공개된다.
- 요약은 STT 도구의 AI가 만든 결과물이라 결정 사항을 후보로만 쓰고, 공유 URL이 있으면 전사와 대조한다.
- 전사를 WebFetch로 읽지 않는다. WebFetch는 페이지를 작은 모델이 다시 요약해서 돌려주므로 원문과 대조할 수 없다.
- 페이지에는 공유 날짜만 있으므로 그 날짜를 쓰고 "추론함"으로 표시한다. 실제 회의 날짜와 다르면 업로더가 고친다.

**플랫폼 레포의 ADR**

ADR의 "무엇" 부분([플랫폼 내부 결정](data-model.md#위키-구조))은 팀이 확인한 뒤에만 결정으로 넣는다.

- ADR은 한 플랫폼이 혼자 정한 기록이다. 그대로 `decided`로 넣으면 팀이 합의하지 않은 것이 확정 정책이 된다. 예: 지도 클러스터를 Android는 "같은 방끼리만 묶는다"로, iOS는 "섞어서 회색으로 묶는다"로 각자 정했다(2026-11-12 확인).
- `source`는 ADR이 아니라 팀이 확인한 회의록이나 채팅이다. 누가 언제 팀 결정으로 확정했는지 남기기 위해서다. ADR은 `## 배경`에 인용한다.
- 확인 전에는 미결로 넣는다. 그래야 플랫폼 간 불일치가 확인될 때까지 위키에 기록된다.

## 흐름

규칙: [procedures/ingest.md 흐름](../procedures/ingest.md#흐름)

각자 PC의 Claude Code에서 ingest 스킬로 실행한다. 개인 구독을 쓰고, 서버와 API 키는 쓰지 않는다. 필요한 도구는 [필요 조건](plugin.md#필요-조건), 위키 clone 위치는 [작업 공간](plugin.md#작업-공간), 실행 모델은 [operations.md](operations.md)를 따른다.

## 승인 구조 (Ownership)

도메인별 담당자는 두지 않는다. 결정은 회의에서 이미 합의된 것이므로, 승인은 LLM이 결정을 빠뜨리거나 지어내지 않았는지 확인하는 단계다.

- 확인은 업로더가 PR을 만들기 전에 Claude Code에서 한다([흐름](../procedures/ingest.md#흐름) 6번). 내용을 가장 잘 아는 사람이기 때문이다.
- 다른 팀원의 승인은 요구하지 않는다. 업로더가 직접 merge한다. 결정 대체가 포함된 PR도 같다.
  - PR을 업로더 본인 계정으로 만들므로, GitHub에서는 자기 PR을 승인할 수 없다.
  - 다른 사람의 승인을 기다리게 하면 회의록마다 PR이 밀린다.
- 누가 확인했는지는 PR 작성자와 merge한 사람으로 남는다.
- 다른 팀원도 PR에 의견을 남기거나 merge할 수 있다.

## 자유 형식 회의록 처리

규칙: [procedures/ingest.md 자유 형식 회의록](../procedures/ingest.md#자유-형식-회의록)

[회의록 템플릿](data-model.md#회의록-템플릿)은 권장 형식이고, 다른 형식의 회의록도 거절하지 않는다. 대신 애매한 항목은 추측하지 않고 "결정 여부 불명확"으로, 추론한 값은 "추론함"으로 표시해 업로더가 확인하게 한다. 확인 항목은 PR 본문에도 남겨 나중에 볼 수 있게 한다.

## 섹션별 반영 위치

규칙: [procedures/ingest.md 반영 위치](../procedures/ingest.md#반영-위치)

결정, 액션 아이템, 미결 사항을 각각 원본별 또는 결정별 파일로 나눠 반영한다. 도메인 페이지는 이 파일들로 생성되므로 ingest가 고치지 않는다([도메인 목록 고정](data-model.md#위키-구조)).

**액션 아이템 완료**

채팅으로 알린 완료도 `raw/notes/`에 남긴다. 누가 언제 완료라고 했는지 기록하기 위해서다.

**미결 해소**

새 결정이 어떤 미결을 풀었는지는 LLM이 후보로만 보여 주고 업로더가 확인한 것만 연결한다. 대체 관계와 같은 이유다. 잘못 연결되면 아직 열린 미결이 도메인 페이지에서 사라진다.

**반영하지 않는 것**

- 코드나 git 이력으로 확인할 수 있는 사실은 넣지 않는다. 금방 낡고, 조회할 때 코드에서 찾으면 된다. 용어집은 예외다([용어집 반영](#용어집-반영)).
- 반영할 내용이 없어도 원본만 담은 PR을 만든다. 원본은 결정이 없어도 보관한다.

## 용어집 반영

규칙: [procedures/ingest.md 용어집 반영](../procedures/ingest.md#용어집-반영)

용어집은 코드에서 확인한 심볼명이라 "코드로 확인할 수 있는 사실은 넣지 않는다"에 해당하지만, 조회가 기획 용어로 코드를 찾으려면 매핑이 필요하므로 예외로 둔다. [기존 자료 이관](#기존-자료-이관)에서는 기준선 PRD를 넣으면서 같은 절차로 채운다.

## 중복·충돌 확인

규칙: [procedures/ingest.md 중복·충돌 확인](../procedures/ingest.md#중복충돌-확인)

기획 문서의 결정이 기존 디자인 결정과 다를 때도 표시한다. PRD는 디자인에서 뽑은 문서라 둘이 어긋날 수 있다. 어느 쪽이 맞는지는 LLM이 판단할 수 없으므로 업로더가 정한다.

## 기존 자료 이관

규칙: [procedures/ingest.md 기존 자료 이관](../procedures/ingest.md#기존-자료-이관)

MVP 개발 중에 쌓인 자료를 한 번 옮긴다. PRD·스펙으로 현재 정책의 기준선을 만들고, 노션 회의록으로 배경을 보충한다. 도메인 목록([`domains.yml`](../domains.yml))은 이관 전에 고정한다. 목록에 없는 도메인은 쓸 수 없기 때문이다.

- 기준선 결정을 `decided`로 넣는 것은 MVP에 구현된 내용이기 때문이다.
- 보충 회의록은 기준선보다 앞선 자료라 기준선 결정을 대체하지 않고 배경에 인용만 한다.
- 보충 회의록의 액션 아이템과 미결 사항은 넣지 않는다. MVP 시기의 항목이라 대부분 끝났거나 의미가 없고, 넣으면 `action-items.md`와 도메인 페이지에 낡은 항목이 쌓인다.
- 이관이 끝나면 `procedures/ingest.md`의 해당 절을 지운다. 한 번만 쓰는 절차라 이후에는 매번 주입할 필요가 없다. 이 절의 이유는 남긴다.

이관 뒤에 들어오는 기획 문서(phase 2 PRD 등)도 팀이 확정본으로 공유한 것만 넣고, 결정은 `decided`로 넣는다. GGUK에는 기획자가 따로 없다. 팀 아이디에이션에서 합의한 내용을 디자이너가 디자인으로 만들고, 그 디자인에서 PRD를 뽑는다. PRD는 이미 합의된 결정을 옮긴 문서라 따로 승인할 사람이 없다. 초안은 넣지 않는다. 초안 단계의 논의는 아이디에이션 회의록으로 들어온다.

## 인덱스 생성과 형식 검사

로드맵 3번에서 `scripts/`를 만들기 전까지는 이 절이 사양이다. 스크립트가 생기면 스크립트가 정본이 되고, 이 절에는 이유만 남긴다.

`scripts/`의 인덱스 생성과 형식 검사는 CI에서만 실행하므로 Python으로 쓴다. 개발자 PC에는 Python을 요구하지 않는다.

**생성 파일은 스크립트가 만든다**

| 파일 | 내용 |
| --- | --- |
| `wiki/domains/<도메인>.md` | 도메인 범위 한 줄, 그 도메인 태그가 달린 `decided` 결정 표(결정일 최신순), `open` 미결 목록. 대체된 결정과 액션 아이템은 넣지 않는다 |
| `wiki/index.md` | 도메인 목차. 도메인, 범위, 결정·미결 건수, 도메인 페이지 링크 |
| `wiki/log.md` | 결정을 `decided_at` 최신순으로 나열한다. 대체된 결정은 `→ 새 결정`으로 표시한다 |
| `wiki/action-items.md` | 열린 액션 아이템을 기한순으로 정렬한다 |

- 각 문서의 frontmatter와 `domains.yml`로 생성한다. LLM과 사람 모두 직접 수정하지 않는다.
- main에 merge된 뒤 CI가 다시 생성해 커밋한다. 같은 입력이면 항상 같은 결과가 나와야 하므로 git 이력이 아니라 파일 내용으로만 만든다.
- 여러 ingest PR이 동시에 같은 파일을 고치면 merge 충돌이 반복되기 때문이다.
- `index.md`와 도메인 페이지를 2단으로 나눈 것은 결정이 늘어나도 조회가 한 번에 읽는 양을 작게 유지하기 위해서다. `index.md` 하나에 모두 넣는 안도 검토했다.
- 도메인 페이지에 대체된 결정을 넣지 않는 것은 조회가 옛 정책으로 답할 위험을 줄이기 위해서다. 이력은 결정 문서의 `supersedes`로 따라간다.
- `action-items.md`는 "기한 지남"을 표시하지 않는다. 생성한 날짜에 따라 결과가 달라지기 때문이다. 기한이 지났는지는 조회할 때 판단한다([위키 조회](retrieval.md#위키-조회)).

**형식 검사는 PR에서 막는다**

CI에서 아래를 검사하고, 실패하면 merge를 막는다([main 보호 규칙](#main-보호-규칙)).

- 결정 문서의 필수 필드와 `status`·`durability` 값, `platforms`가 1개 이상 있는지. `platforms`가 비면 플랫폼별로 결정을 거르는 기능([MCP 서버](backlog/mcp-server.md), [훅](backlog/hooks.md))에서 그 결정이 어디에도 나오지 않는다
- 결정 파일 이름의 날짜가 `decided_at`과 같은지. 다르면 `log.md`의 순서와 파일 이름이 다른 날짜를 가리킨다
- 결정 문서의 `source`, `supersedes`, `superseded_by`가 가리키는 파일이 실제로 있는지
- 대체 표시가 짝이 맞는지: `superseded`와 `superseded_by`가 함께 있는지, 새 결정의 `supersedes`와 이전 결정의 `superseded_by`가 서로를 가리키는지. 반만 처리하면 옛 결정이 도메인 페이지에 유효한 결정으로 남는다
- 액션 아이템 파일의 필수 필드와 `status` 값, `source`가 가리키는 파일이 실제로 있는지
- 미결 파일의 필수 필드와 `status` 값, `source`가 가리키는 파일이 실제로 있는지, `resolved`이면 `resolved_by`가 있고 그 파일이 실제로 있는지, `resolved`가 아니면 `resolved_by`가 없는지
- 액션 아이템·미결 파일의 경로가 원본의 `raw/` 아래 경로를 따르는지. 어긋나면 한 원본의 항목이 여러 파일로 흩어진다
- `domains` 값이 `domains.yml`에 있는지, 결정과 미결 항목에 `domains`가 1개 이상 있는지
- `domains.yml`의 이름이 영어 소문자와 하이픈으로 되어 있고 겹치지 않는지
- `raw/`의 기존 파일을 고치거나 지우지 않았는지
- 생성 파일(`wiki/domains/`, `index.md`, `log.md`, `action-items.md`)을 추가하거나 고치지 않았는지. PR에서 고친 내용은 merge 뒤 CI가 덮어써 조용히 사라지기 때문이다. 삭제는 허용한다. 생성 파일을 없앨 때 남은 파일을 지울 수 있어야 하고, 잘못 지워도 CI가 다시 만든다

본문 섹션은 검사하지 않는다. 본문은 업로더가 확인한다.

**검사 스크립트의 테스트**

- 템플릿을 채운 샘플 문서가 형식 검사를 통과하는지 확인한다. 상태 값과 필수 필드가 템플릿과 검사 코드 양쪽에 있으므로, 둘이 어긋나면 이 테스트가 잡는다.
- 한글 파일 이름이 macOS(NFD)와 CI(Linux, NFC)에서 같게 다뤄지는지 확인한다. `source` 경로 비교가 정규화 차이로 실패할 수 있다.

형식 검사는 PR 쪽 코드로 실행되므로, 같은 PR에서 검사 스크립트를 고치면 피할 수 있다. LLM의 실수를 막는 장치이고 의도적인 우회는 막지 않는다.

## main 보호 규칙

위키 레포는 public이다. Free 플랜의 private 레포에서는 ruleset을 쓸 수 없어서 공개로 정했다. 공개에 따른 규칙은 [공개 범위](data-model.md#공개-범위)를 따른다.

- main은 ruleset으로 아래를 강제한다.
  - PR을 거쳐야 merge할 수 있다. 승인 수는 0명이다([승인 구조](#승인-구조-ownership)).
  - 형식 검사가 통과해야 merge할 수 있다.
  - force push와 브랜치 삭제를 막는다.
- ruleset은 두 번에 나눠 건다([다음 단계](README.md#로드맵)). 형식 검사 필수와 GitHub App 우회는 형식 검사 CI가 merge된 뒤에 추가한다. 필수 검사가 보고되지 않으면 PR이 "Waiting for status to be reported" 상태로 막히기 때문이다.
- PR 없이 main에 커밋하는 곳은 CI 하나뿐이다. CI는 GitHub App 토큰으로 생성 파일을 다시 만들어 커밋하고, 이 App만 ruleset 우회 대상으로 둔다. ruleset 우회 대상에는 GitHub App을 넣을 수 있다.
- App secrets가 없으면 기본 `GITHUB_TOKEN`으로 커밋한다. ruleset이 없는 동안(1.3 전)에는 기본 토큰으로도 main에 커밋할 수 있어서, App을 만들기 전에도 생성 파일이 갱신된다. ruleset을 건 뒤에는 기본 토큰이 우회 대상이 아니므로 App이 있어야 한다.
- ruleset은 우회 대상이 고칠 경로를 제한하지 못한다. 생성 파일 밖을 고치지 않는 것은 CI 코드가 지킨다.
- App 토큰으로 만든 커밋은 워크플로를 다시 실행한다. 재생성 결과가 바뀌지 않으면 커밋하지 않으므로 한 번에 멈춘다. 기본 토큰으로 만든 커밋은 워크플로를 다시 실행하지 않는다.

**GitHub App과 비밀값**

| 항목 | 내용 |
| --- | --- |
| App 권한 | `gguk-wiki` Contents: Write |
| 비밀값 | `WIKI_APP_ID`, `WIKI_APP_PRIVATE_KEY`를 GitHub Actions secrets에 둔다. GitHub는 `GITHUB_`로 시작하는 secret 이름을 허용하지 않는다([GitHub 문서](https://docs.github.com/en/actions/reference/security/secrets)) |
| 노출 방지 | 인덱스 재생성 워크플로는 main push에서만 실행한다. 외부 fork PR에는 secrets가 전달되지 않으므로, PR 형식 검사는 secrets 없이 돈다 |
