# Ingest (쓰기 경로)

위키에 정보가 반영되는 흐름을 왜 그렇게 정했는지 적는다. 규칙의 정본은 [procedures/ingest.md](../procedures/ingest.md)이고, 저장 형식은 [data-model.md](data-model.md)를 따른다.

## 입력

규칙: [procedures/ingest.md 입력](../procedures/ingest.md#입력)

입력은 회의록 파일, 노션 회의록(MCP, 내보내기), STT 요약(Alt), 채팅, 플랫폼 레포의 ADR이다. 기획서는 [기존 자료 이관](#기존-자료-이관)의 기준선으로만 받고, 스펙 문서와 플랫폼 레포의 다른 기술 문서(Node PRD 등)는 받지 않는다([플랫폼 내부 결정](data-model.md#위키-구조)).

- 어떤 입력이든 원본을 `raw/`에 먼저 남긴다. 모든 결정의 `source`가 원본을 가리키게 하기 위해서다.
- 기획서와 스펙 문서는 넣지 않는다. 앞으로 기획서는 위키로 뽑고 스펙 문서는 기획서에서 뽑는 문서라([운영 방향](direction.md#흐름)), 넣으면 위키에서 나온 내용이 다시 원본이 되어 `source`가 회의나 채팅이 아닌 위키 자신을 가리킨다. 그 문서에만 있는 결정은 그 결정을 정한 회의록이나 채팅으로 넣는다. 이관 기준선 기획서는 위키가 생기기 전의 문서라 예외다.
- 채팅 입력은 요약하거나 보충하지 않는다. 원본이 LLM의 해석이 되면 `source`로서 의미가 없다.
- 남의 말을 전달받으면 인용된 발언만이 아니라 전달 맥락("민지가 ~래")까지 적는다. 누가 누구에게 들었는지도 원본이다.
- 업로더 본인의 채팅이면 `gh api user`의 아이디로 [`people.yml`](../people.yml)에서 찾은 이름을 `author`로 쓴다([인물 목록](data-model.md#위키-구조)). 본인 아이디로 찾으므로 이름과 잘못 짝지을 일이 없다. 회귀 검증 장면 3은 `author`를 비워 두고 묻고, 장면 5는 채운 뒤 물어 세션마다 갈렸다. 남의 말인지 모를 때만 묻는다.
- 업로더의 보충 답(어느 항목인지, 누가 언제 말했는지)은 같은 `raw/notes/` 파일에 이어 적는다. 로드맵 5번 검증에서 완료 알림 원본에는 "튜토리얼 그거 끝났어"만 남고, 어느 항목인지 정한 답은 PR 본문에만 남았다. `source`가 가리키는 원본만으로 근거를 알 수 있어야 한다. merge 전 작업 브랜치에서 쓰는 중인 파일이므로 "`raw/`는 넣은 뒤 고치지 않는다"와 부딪히지 않는다. 확인 항목의 승인·거절은 원본 내용이 아니라 ingest 과정의 판단이므로 PR 본문에 남긴다.

**노션 회의록**

- MCP 설정은 [필요 조건](plugin.md#필요-조건)을 따른다. 노션 페이지를 만들거나 고치는 도구는 쓰지 않는다. 위키는 노션을 읽기만 한다.
- 내보내기는 페이지 속성이 frontmatter가 아니라 제목 아래 `Key: Value` 줄로 나오므로 `date`와 `domains`를 추론한다([자유 형식 회의록 처리](#자유-형식-회의록-처리)).
- MCP는 사람 멘션에 그 사람의 이메일을 붙여 돌려준다. 팀 회의록 템플릿의 "누구" 칸이 멘션이라, 그대로 두면 노션 회의록 대부분이 [공개 범위](data-model.md#공개-범위)에 걸려 멈춘다. 이메일은 작성자가 쓴 내용이 아니라 MCP가 붙인 것이므로, 멘션을 이름으로 바꾸는 것은 원본 수정이 아니라 형식 변환으로 본다. 업로더가 노션에서 멘션을 글자로 바꾼 뒤 넣는 안, 내보내기 파일로 넣는 안도 검토했다.
- 페이지 속성에 Alt 공유 URL이 들어 있을 수 있다. 회귀 검증 장면 2-B에서 후보로 받은 6차 페이지의 "Alt 정리" 속성에 있었다. MCP 본문은 그대로 저장하므로 속성까지 `raw/`에 들어간다. [STT 요약](#입력)의 공유 URL과 같은 이유로 저장하지 않고, 같은 방식으로 전사와 대조한다. 회의 내용이 아니라 전사로 가는 링크이므로 값을 비우는 것은 멘션처럼 형식 변환으로 본다. 공개 범위 금지 표에 공유 링크를 더해 멈추고 업로더가 노션에서 지운 뒤 다시 넣게 하는 안도 검토했다.

**STT 요약 (Alt)**

- 전사와 공유 URL은 저장하지 않는다. 공유 URL은 로그인 없이 열리므로, public 레포에 남기면 전사 전체가 공개된다.
- 요약은 STT 도구의 AI가 만든 결과물이라 결정 사항을 후보로만 쓰고, 공유 URL이 있으면 전사와 대조한다.
- 전사를 WebFetch로 읽지 않는다. WebFetch는 페이지를 작은 모델이 다시 요약해서 돌려주므로 원문과 대조할 수 없다.
- 페이지에는 공유 날짜만 있으므로 그 날짜를 쓰고 "추론함"으로 표시한다. 실제 회의 날짜와 다르면 업로더가 고친다.

**플랫폼 레포의 ADR**

ADR에서 위키에 넣는 부분(사용자에게 보이는 동작, 두 플랫폼 이상이 지키는 계약과 기술 결정. [플랫폼 내부 결정](data-model.md#위키-구조))은 팀이 확인한 뒤에만 결정으로 넣는다.

- ADR은 한 플랫폼이 혼자 정한 기록이다. 그대로 `decided`로 넣으면 팀이 합의하지 않은 것이 확정 정책이 된다. 예: 지도 클러스터를 Android는 "같은 방끼리만 묶는다"로, iOS는 "섞어서 회색으로 묶는다"로 각자 정했다(2026-11-12 확인).
- `source`는 ADR이 아니라 팀이 확인한 회의록이나 채팅이다. 누가 언제 팀 결정으로 확정했는지 남기기 위해서다. ADR은 `## 배경`에 인용한다.
- 확인 전에는 미결로 넣는다. 그래야 플랫폼 간 불일치가 확인될 때까지 위키에 기록된다.
- 계약은 받아 쓰는 방식을 빼고 계약 자체만 넣는다. 받아 쓰는 방식까지 넣으면 한 플랫폼의 구현이 공통 결정처럼 보인다.

## 흐름

규칙: [procedures/ingest.md 흐름](../procedures/ingest.md#흐름)

각자 PC의 Claude Code에서 ingest 스킬로 실행한다. 개인 구독을 쓰고, 서버와 API 키는 쓰지 않는다. 필요한 도구는 [필요 조건](plugin.md#필요-조건), 위키 clone 위치는 [작업 공간](plugin.md#작업-공간), 실행 모델은 [operations.md](operations.md)를 따른다.

- 위키 clone 하나를 여러 세션이 같이 쓸 수 있다. 검증에서 한 세션이 다른 세션의 PR을 merge하려 한 적이 있다. 그래서 세션은 merge하지 않고 자기가 만든 브랜치와 PR만 다룬다. 시작할 때 default 브랜치가 아니면 멈추는 것도 다른 세션의 작업 브랜치 위에서 시작하지 않기 위해서다. PR 뒤 default 브랜치로 돌아가는 것은 다음 ingest가 이 검사에 걸리지 않게 하기 위해서다.
- 커밋하지 않은 변경은 버리지 않고 stash로만 치운다. 검증에서 "알아서 치우고 진행해줘"에 세션이 `git checkout --`로 되돌려 복구할 수 없었다.
- 멈출 때 바뀔 파일 목록과 치우는 방법을 이미 보여 줬으면, 그 뒤의 치우라는 답을 확인으로 본다. 업로더는 목록을 보고 답한 것이다. 회귀 검증 장면 3에서 세션이 이렇게 바로 stash했고, 업로더가 보지 못한 파일을 치우지 않았다. 답 뒤에 목록을 다시 보여 주고 한 번 더 확인받는 안도 검토했다.
- 공개 범위, 이관 여부, 같은 원본은 작업 브랜치를 만들기 전에 확인한다. 셋 다 멈출 수 있는 확인이라, 브랜치를 먼저 만들면 멈춘 뒤 빈 작업 브랜치가 남는다. 회귀 검증 장면 1-a·2의 세션도 규칙과 달리 브랜치를 만들기 전에 확인했다.
- PR 없이 끝나면 자기가 만든 작업 브랜치를 지우고 default 브랜치로 돌아간다. 다음 ingest가 흐름 1의 브랜치 검사에 걸리지 않게 하기 위해서다(회귀 검증 장면 3).
- 같은 원본이 이미 `raw/`에 있으면 멈춘다. 회귀 검증 장면 2에서 이미 들어간 노션 회의록을 다시 받았다. `raw/`는 고칠 수 없으므로 넣는다면 새 파일이 되고, 같은 원본이 두 번 들어간다. 원본이 바뀐 경우만 새 파일로 넣을지 묻는다.
- PR 뒤 형식 검사 결과를 세션이 확인한다. 검증에서 날짜를 바꾸면서 미결 파일의 `source` 1곳을 놓쳐 첫 검사가 실패했다. 로컬 `check.py`는 선택이다. 개발자 PC에 Python을 요구하지 않기 위해서다([인덱스 생성과 형식 검사](#인덱스-생성과-형식-검사)).

## 승인 구조 (Ownership)

도메인별 담당자는 두지 않는다. 결정은 회의에서 이미 합의된 것이므로, 승인은 LLM이 결정을 빠뜨리거나 지어내지 않았는지 확인하는 단계다.

- 확인은 업로더가 PR을 만들기 전에 Claude Code에서 한다([흐름](../procedures/ingest.md#흐름) 7번). 내용을 가장 잘 아는 사람이기 때문이다.
- 다른 팀원의 승인은 요구하지 않는다. 업로더가 직접 merge한다. 결정 대체가 포함된 PR도 같다.
  - PR을 업로더 본인 계정으로 만들므로, GitHub에서는 자기 PR을 승인할 수 없다.
  - 다른 사람의 승인을 기다리게 하면 회의록마다 PR이 밀린다.
- 누가 확인했는지는 PR 작성자와 merge한 사람으로 남는다.
- 다른 팀원도 PR에 의견을 남기거나 merge할 수 있다.

**확인 항목의 답**

규칙: [procedures/ingest.md 업로더 확인 항목](../procedures/ingest.md#업로더-확인-항목)

- 확인 항목마다 답이 없을 때의 처리를 정해 둔다. 검증에서 "진행" 한마디를 어떤 세션은 용어집 후보까지 승인한 것으로 보고, 어떤 세션은 답이 없는 용어집 후보를 뺐다.
- 넣거나 연결하는 항목은 답이 없으면 넣지 않는다. 업로더가 보지 않은 변경이 위키에 들어가지 않게 하기 위해서다. 추론값은 넣지 않으면 필드가 비므로 추론값을 쓴다.
- 지시를 넓혀 해석하지 않는다. 검증에서 "제외하고 넣어"를 이메일뿐 아니라 개인 사정 문장 삭제까지로 넓힌 일이 있었다.
- 항목마다 답을 받아야만 진행하는 안도 검토했다.
- "결정 여부 불명확"은 답이 없으면 결정이나 미결로 넣지 않고 PR 본문에만 남긴다. 회귀 검증 장면 6은 미결로 넣고 장면 5는 넣지 않아 세션마다 갈렸다. 미결로 넣으면 업로더가 보지 않은 항목이 도메인 페이지의 미결 목록에 오른다.

## 자유 형식 회의록 처리

규칙: [procedures/ingest.md 자유 형식 회의록](../procedures/ingest.md#자유-형식-회의록)

[회의록 템플릿](data-model.md#회의록-템플릿)은 권장 형식이고, 다른 형식의 회의록도 거절하지 않는다. 대신 애매한 항목은 추측하지 않고 "결정 여부 불명확"으로, 추론한 값은 "추론함"으로 표시해 업로더가 확인하게 한다. 확인 항목은 PR 본문에도 남겨 나중에 볼 수 있게 한다.

## 섹션별 반영 위치

규칙: [procedures/ingest.md 반영 위치](../procedures/ingest.md#반영-위치)

결정, 액션 아이템, 미결 사항을 각각 원본별 또는 결정별 파일로 나눠 반영한다. 도메인 페이지는 이 파일들로 생성되므로 ingest가 고치지 않는다([도메인 목록 고정](data-model.md#위키-구조)).

**액션 아이템 완료**

채팅으로 알린 완료도 `raw/notes/`에 남긴다. 누가 언제 완료라고 했는지 기록하기 위해서다.

**미결 해소**

새 결정이 어떤 미결을 풀었는지는 LLM이 후보로만 보여 주고 업로더가 확인한 것만 연결한다. 대체 관계와 같은 이유다. 잘못 연결되면 아직 열린 미결이 도메인 페이지에서 사라진다.

**반영하지 않는 것**

- 코드나 git 이력으로 확인할 수 있는 사실은 넣지 않는다. 금방 낡고, 조회할 때 코드에서 찾으면 된다. 용어집은 예외다([용어집 반영](#용어집-반영)). 결정의 의도와 이유는 코드에서 알 수 없으므로 넣는다. 계약 결정도 같다.
- API 명세의 엔드포인트별 필드 목록은 옮기지 않는다. 화면 정의를 Figma에 두는 것과 같은 이유다([진실의 기준](data-model.md#진실의-기준-source-of-truth)).
- 반영할 내용이 없어도 원본만 담은 PR을 만든다. 원본은 결정이 없어도 보관한다.

## 용어집 반영

규칙: [procedures/ingest.md 용어집 반영](../procedures/ingest.md#용어집-반영)

용어집은 코드에서 확인한 심볼명이라 "코드로 확인할 수 있는 사실은 넣지 않는다"에 해당하지만, 조회가 기획 용어로 코드를 찾으려면 매핑이 필요하므로 예외로 둔다. [기존 자료 이관](#기존-자료-이관)에서는 기준선 기획서를 넣으면서 같은 절차로 채운다.

## 중복·충돌 확인

규칙: [procedures/ingest.md 중복·충돌 확인](../procedures/ingest.md#중복충돌-확인)

기획 문서의 결정과 기존 디자인 결정을 대조하던 확인은 2026-11-27에 지웠다. 기획서를 ingest하지 않게 되면서(이관 기준선만 한 번 넣고, 그때 위키에는 디자인 결정이 없다) 걸릴 일이 없어졌다. 새 흐름에서 어긋남은 위키 → 기획서 → Figma 순서에서 Figma 쪽에 생기므로, 디자인 리뷰에서 사람이 찾는다([운영 방향](direction.md#흐름)).

- 기존 결정에서 탈락한 대안을 새 결정이 채택하면 대체 후보로 본다. 검증에서 "위임 대상 선택 모달"(자동 위임은 검토 후 탈락)과 새 "방장 자동 위임"을 별개로 넣어, 상반된 두 결정이 모두 `decided`로 남을 뻔했다.
- 같은 전제의 다른 결정을 함께 보여 주는 것은 하나만 대체하면 나머지가 낡은 전제로 남기 때문이다. 검증에서 "소셜 로그인 제외"만 대체되고 같은 전제의 "비회원 익명 세션"은 `decided`로 남았다.
- 같은 전제는 대체 후보 결정의 `## 결정`이 정한 규칙을 인용하거나 그 규칙에 기대는 결정으로 정한다. 회귀 검증 장면 1·3·5에서 세션마다 2~3건씩 골랐지만 고른 기준을 밝힌 세션은 없었다. 결정마다 기대는 규칙을 밝히면 업로더가 목록이 맞는지 판단할 수 있다.
- 업로더가 대체를 확인하기 전에는 작업 트리에서도 이전 결정 파일을 고치지 않는다. 회귀 검증 장면 5에서 세션이 답 전에 이전 결정을 `superseded`로 바꿔 두었다. 답이 없으면 되돌려야 하는데, 되돌리기를 빠뜨리면 확인하지 않은 대체가 PR에 들어간다.

## 기존 자료 이관

규칙: [procedures/ingest.md 기존 자료 이관](../procedures/ingest.md#기존-자료-이관)

MVP 개발 중에 쌓인 자료를 한 번 옮긴다. MVP까지 구현된 내용을 담은 기획서로 현재 정책의 기준선을 만들고, 회의록과 채팅 기록으로 배경을 보충한다. 도메인 목록([`domains.yml`](../domains.yml))은 이관 전에 고정한다. 목록에 없는 도메인은 쓸 수 없기 때문이다.

스펙 문서는 기준선에 넣지 않는다. 기획서에서 뽑은 문서라 기획서와 내용이 겹치고, 둘이 다르면 기준선이 둘로 갈린다. 기획서와 스펙을 함께 넣고 다른 곳을 업로더가 정하는 안도 검토했다.

- 이관 PR에서 `domains.yml`을 고치지 않는 것은 이관 PR이 원본마다 여러 개 열리기 때문이다. 한 PR에서 고친 목록은 merge 전까지 다른 세션에 주입되지 않아, 이름이 갈라지거나 같은 `scope` 줄을 고쳐 충돌하기 쉽다. 목록은 기획서에서 뽑았으므로 이관 중에 맞는 도메인이 없으면 목록이 덜 된 것이다. 평소 ingest처럼 이관 PR에 함께 넣는 안도 검토했다.
- 기준선 결정을 `decided`로 넣는 것은 MVP에 구현된 내용이기 때문이다.
- 계약 기준선은 만들지 않는다. 기준선 기획서에는 계약이 없다. 서버 API 명세로 기준선을 만드는 안도 검토했지만, 명세는 코드에서 나온 현재 동작이라 팀이 정한 결정의 원본이 아니다. 지금의 계약은 명세가 실제 동작으로 남고, 조회가 대조한다.
- 보충 회의록은 기준선보다 앞선 자료라 기준선 결정을 대체하지 않고 배경에 인용만 한다.
- 이 인용은 기존 결정 파일을 고치는 일이라 [결정 대체](../procedures/ingest.md#결정-대체)의 예외다. 예외를 결정 대체 절이 아니라 이관 절에 적는 것은 이관이 끝나 절을 지울 때 예외도 함께 없어지게 하기 위해서다.
- 이관 중에는 회의록이 보충인지 새 회의인지 입력만으로 갈리지 않으면 묻는다. 검증에서 노션 URL만 받은 세션이 이관 보충 회의록을 일반 ingest로 처리해, 새 결정과 도메인을 만들고 기준선 결정을 대체했다. 같은 내용을 "이관 보충"이라고 적어 넣으면 기대대로 처리했다.
- 이관 질문은 확인 항목 표 밖의 필수 질문이라 지목 없는 답으로 대신하지 않고, 답이 없으면 진행하지 않는다. 보충인지 새 회의인지에 따라 대체, 액션 아이템, 미결 처리가 모두 달라져 정해 둘 기본 처리가 없다. 회귀 검증 장면 2·2-B에서 세션이 답이 없을 때의 처리를 각자 붙였다. `raw/`를 넣기 전에 묻는 것은 답에 따라 넣지 않을 수 있기 때문이다.
- 기준선 PR 본문에 코드와 다른 곳을 반드시 적는 것은 적지 않으면 대조를 안 한 것인지 다른 곳이 없는 것인지 구분할 수 없기 때문이다.
- 보충 회의록의 액션 아이템과 미결 사항은 넣지 않는다. MVP 시기의 항목이라 대부분 끝났거나 의미가 없고, 넣으면 `action-items.md`와 도메인 페이지에 낡은 항목이 쌓인다.
- 이관이 끝나면 `procedures/ingest.md`의 해당 절을 지운다. 한 번만 쓰는 절차라 이후에는 매번 주입할 필요가 없다. 이 절의 이유는 남긴다.

이관 뒤에는 기획서(phase 2 기획서 등)와 스펙 문서를 넣지 않는다. 지금까지는 팀 아이디에이션에서 합의한 내용을 디자이너가 디자인으로 만들고, 그 디자인에서 기획서를 뽑았다. 앞으로는 회의 내용을 위키에 넣고 위키로 기획서를 뽑는다([운영 방향](direction.md#흐름)). 이관 기준선도 팀이 확정본으로 공유한 것만 넣는다. 초안 단계의 논의는 회의록으로 들어온다.

## 인덱스 생성과 형식 검사

로드맵 3번에서 `scripts/`를 만들기 전까지는 이 절이 사양이다. 스크립트가 생기면 스크립트가 정본이 되고, 이 절에는 이유만 남긴다.

`scripts/`의 인덱스 생성과 형식 검사는 CI에서만 실행하므로 Python으로 쓴다. 개발자 PC에는 Python을 요구하지 않는다.

**생성 파일은 스크립트가 만든다**

| 파일 | 내용 |
| --- | --- |
| `wiki/domains/<도메인>.md` | 도메인 범위 한 줄, 그 도메인 태그가 달린 `decided` 결정 표(결정일 최신순), `open` 미결 목록. 대체된 결정과 액션 아이템은 넣지 않는다 |
| `wiki/index.md` | 도메인 목차. 도메인, 범위, 결정·미결 건수, 도메인 페이지 링크 |
| `wiki/log.md` | 결정을 `decided_at` 최신순으로 나열한다. 대체된 결정은 `→ 새 결정`으로 표시한다 |
| `wiki/action-items.md` | 열린 액션 아이템을 기한순으로 정렬한다 |

- 각 문서의 frontmatter와 `domains.yml`로 생성한다. LLM과 사람 모두 직접 수정하지 않는다.
- main에 merge된 뒤 CI가 다시 생성해 커밋한다. 같은 입력이면 항상 같은 결과가 나와야 하므로 git 이력이 아니라 파일 내용으로만 만든다.
- 여러 ingest PR이 동시에 같은 파일을 고치면 merge 충돌이 반복되기 때문이다.
- `index.md`와 도메인 페이지를 2단으로 나눈 것은 결정이 늘어나도 조회가 한 번에 읽는 양을 작게 유지하기 위해서다. `index.md` 하나에 모두 넣는 안도 검토했다.
- 도메인 페이지에 대체된 결정을 넣지 않는 것은 조회가 옛 정책으로 답할 위험을 줄이기 위해서다. 이력은 결정 문서의 `supersedes`로 따라간다.
- `action-items.md`는 "기한 지남"을 표시하지 않는다. 생성한 날짜에 따라 결과가 달라지기 때문이다. 기한이 지났는지는 조회할 때 판단한다([위키 조회](retrieval.md#위키-조회)).

**형식 검사는 PR에서 막는다**

CI에서 아래를 검사하고, 실패하면 merge를 막는다([main 보호 규칙](#main-보호-규칙)).

- 결정 문서의 필수 필드와 `status`·`durability` 값, `platforms`가 1개 이상 있는지. `platforms`가 비면 플랫폼별로 결정을 거르는 기능(MCP 서버, 훅)에서 그 결정이 어디에도 나오지 않는다
- 결정 파일 이름의 날짜가 `decided_at`과 같은지. 다르면 `log.md`의 순서와 파일 이름이 다른 날짜를 가리킨다
- 결정 문서의 `source`, `supersedes`, `superseded_by`가 가리키는 파일이 실제로 있는지, `supersedes`·`superseded_by`는 `wiki/decisions/` 아래 결정 문서를 가리키는지. 다른 파일을 가리키면 대신할 결정 없이 결정이 도메인 페이지에서 빠진다
- `superseded_by`가 경로 하나인지, `supersedes` 목록에 같은 경로가 두 번 있지 않은지. 옛 결정마다 지금 유효한 결정이 하나로 정해져야 한다([결정 문서 형식](data-model.md#결정-문서-형식))
- 대체 표시가 짝이 맞는지: `superseded`와 `superseded_by`가 함께 있는지, 새 결정의 `supersedes`에 이전 결정이 있고 이전 결정의 `superseded_by`가 새 결정을 가리키는지. 반만 처리하면 옛 결정이 도메인 페이지에 유효한 결정으로 남는다. 대체 관계가 순환하지 않는지. 순환하면 짝이 맞아도 사슬에 `decided` 결정이 없어 그 주제가 도메인 페이지에서 사라진다
- 액션 아이템 파일의 필수 필드와 `status` 값, `source`가 가리키는 파일이 실제로 있는지
- 새로 추가하거나 고친 액션 아이템의 `assignee`가 1명 이상인 목록이고, 원소가 `people.yml`의 `name`이나 "알 수 없음", "미정"이며 겹치지 않는지. 목록 밖 이름이 들어가면 동의하지 않은 사람의 이름이 public 레포에 남는다([인물 목록](data-model.md#위키-구조)). 이 규칙 전에 들어간 파일은 형식이 달라(문자열 담당자, 담당자 없음) PR에서 바뀌지 않으면 검사하지 않는다. 고치면(완료 표시 등) 그 파일의 모든 항목을 새 형식으로 검사한다
- 미결 파일의 필수 필드와 `status` 값, `source`가 가리키는 파일이 실제로 있는지, `resolved`이면 `resolved_by`가 있고 그 파일이 실제로 있는 결정 문서인지, `resolved`가 아니면 `resolved_by`가 없는지
- 액션 아이템·미결 파일의 경로가 원본의 `raw/` 아래 경로를 따르는지. 어긋나면 한 원본의 항목이 여러 파일로 흩어진다
- `domains` 값이 `domains.yml`에 있는지, 결정과 미결 항목에 `domains`가 1개 이상 있는지
- 결정과 미결 항목의 `kind` 값, `tech` 결정의 `platforms`에 코드 레포가 있는 플랫폼(`platform-repository.yml`) 2개 이상이 있는지. 하나뿐인 `tech` 결정은 그 레포에서 관리할 플랫폼 내부 결정이다([결정 종류](data-model.md#결정-문서-형식))
- `domains.yml`의 이름이 영어 소문자와 하이픈으로 되어 있고 겹치지 않는지
- `people.yml`의 `name`, `github`가 겹치지 않는지, `role`이 `platforms`와 같은 값인지, `name`이 "알 수 없음"·"미정"이 아닌지
- `platform-repository.yml`의 `platform`이 `platforms` 값(`design` 제외)이고 겹치지 않는지, `url`이 `https://github.com/<조직>/<레포>` 형식이고 레포 이름이 겹치지 않는지. 레포 이름이 작업 공간의 폴더 이름이 되므로 겹치면 한 레포만 clone된다
- 새로 추가한 채팅 원본(`raw/notes/`)에 `author`가 있고, `people.yml`의 `name`이나 "알 수 없음"인지. 원본은 넣은 뒤 고칠 수 없어, 빠지거나 목록 밖 이름으로 merge되면 다시 고칠 수 없다
- `raw/`의 기존 파일을 고치거나 지우지 않았는지
- 생성 파일(`wiki/domains/`, `index.md`, `log.md`, `action-items.md`)을 추가하거나 고치지 않았는지. PR에서 고친 내용은 merge 뒤 CI가 덮어써 조용히 사라지기 때문이다. 삭제는 허용한다. 생성 파일을 없앨 때 남은 파일을 지울 수 있어야 하고, 잘못 지워도 CI가 다시 만든다

본문 섹션은 검사하지 않는다. 본문은 업로더가 확인한다.

**검사 스크립트의 테스트**

- 템플릿을 채운 샘플 문서가 형식 검사를 통과하는지 확인한다. 상태 값과 필수 필드가 템플릿과 검사 코드 양쪽에 있으므로, 둘이 어긋나면 이 테스트가 잡는다.
- 한글 파일 이름이 macOS(NFD)와 CI(Linux, NFC)에서 같게 다뤄지는지 확인한다. `source` 경로 비교가 정규화 차이로 실패할 수 있다.

형식 검사는 PR 쪽 코드로 실행되므로, 같은 PR에서 검사 스크립트를 고치면 피할 수 있다. LLM의 실수를 막는 장치이고 의도적인 우회는 막지 않는다.

## main 보호 규칙

위키 레포는 public이다. Free 플랜의 private 레포에서는 ruleset을 쓸 수 없어서 공개로 정했다. 공개에 따른 규칙은 [공개 범위](data-model.md#공개-범위)를 따른다.

- main은 ruleset으로 아래를 강제한다.
  - PR을 거쳐야 merge할 수 있다. 승인 수는 0명이다([승인 구조](#승인-구조-ownership)).
  - 형식 검사가 통과해야 merge할 수 있다.
  - force push와 브랜치 삭제를 막는다.
- ruleset은 형식 검사 CI와 GitHub App이 준비된 뒤 한 번에 건다([다음 단계](README.md#로드맵)). 필수 검사를 보고하는 CI가 없는 상태에서 걸면 PR이 "Waiting for status to be reported" 상태로 막히기 때문이다.
- PR 없이 main에 커밋하는 곳은 CI 하나뿐이다. CI는 GitHub App 토큰으로 생성 파일을 다시 만들어 커밋하고, 이 App만 ruleset 우회 대상으로 둔다. ruleset 우회 대상에는 GitHub App을 넣을 수 있다.
- App secrets가 없으면 기본 `GITHUB_TOKEN`으로 커밋한다. ruleset이 없는 동안(1.3 전)에는 기본 토큰으로도 main에 커밋할 수 있어서, App을 만들기 전에도 생성 파일이 갱신된다. ruleset을 건 뒤에는 기본 토큰이 우회 대상이 아니므로 App이 있어야 한다.
- ruleset은 우회 대상이 고칠 경로를 제한하지 못한다. 생성 파일 밖을 고치지 않는 것은 CI 코드가 지킨다.
- App 토큰으로 만든 커밋은 워크플로를 다시 실행한다. 재생성 결과가 바뀌지 않으면 커밋하지 않으므로 한 번에 멈춘다. 기본 토큰으로 만든 커밋은 워크플로를 다시 실행하지 않는다.

**GitHub App과 비밀값**

| 항목 | 내용 |
| --- | --- |
| App 권한 | `gguk-wiki` Contents: Write |
| 비밀값 | `WIKI_APP_ID`, `WIKI_APP_PRIVATE_KEY`를 GitHub Actions secrets에 둔다. GitHub는 `GITHUB_`로 시작하는 secret 이름을 허용하지 않는다([GitHub 문서](https://docs.github.com/en/actions/reference/security/secrets)) |
| 노출 방지 | 인덱스 재생성 워크플로는 main push에서만 실행한다. 외부 fork PR에는 secrets가 전달되지 않으므로, PR 형식 검사는 secrets 없이 돈다 |
