# 검색 고도화

> 상태: backlog. 미룬 이유는 [backlog/](README.md)를 따른다.

1단계 조회는 Claude가 검색어를 만들고 grep한다([질의 정규화](../retrieval.md#질의-정규화)). 이 방식으로 부족해지면 아래를 순서대로 검토한다.

## 형태소 분석기 정규화

검색어를 LLM이 아니라 코드가 만들어야 할 때 필요하다. MCP `search_wiki`가 질문 문장을 그대로 받거나([서버 지시문](mcp-server.md#서버-지시문)), [프롬프트 입력 훅](hooks.md#프롬프트-입력-훅)이 프롬프트에서 검색어를 뽑는 경우다.

- 조사·어미 제거를 규칙으로 하면 틀리기 쉽다. "결제가"의 '가'는 조사지만 "가격"의 '가'는 아니다.
- kiwipiepy(Kiwi 형태소 분석기)로 형태소 단위로 나눠 체언과 식별자만 남긴다. 이는 R@5에 직접 영향을 준다.
- 정규화 결과가 항상 같으므로 클라이언트와 관계없이 같은 결과가 나오고, 평가셋으로 비교할 수 있다.
- 서버 구현 스택은 [구현 스택](hosting/app.md#구현-스택)을 따른다.

## 검색 평가셋

- 실제 질문과 정답 페이지 쌍 20~40개로 시작해 `evals/search.jsonl`에 둔다.
- 질문은 페이지 제목을 그대로 쓰지 않고 실제 사람이 묻는 말투로 쓴다.
- 위키에 답이 없어야 정답인 질문도 포함한다.
- 지표: 상위 5건 안에 정답이 있는 비율(R@5), 답이 없는 질문에 엉뚱한 답을 낸 비율.
- 검색 방식을 바꿀 때마다 돌려 비교한다. 아래 벡터 DB 도입 여부도 이 수치로 판단한다.

## 벡터 DB

> **메모: 위키 검색에도 벡터 DB가 필요한가?**
>
> 당장은 필요 없다. 도입 시점만 미리 정해 둔다.
>
> - **지금 안 쓰는 이유**
>   - 위키는 Ingest 단계에서 이미 정리된다(도메인 페이지, `index.md`, `glossary.md`). 목차를 따라 찾는 편이 유사도 검색보다 정확하다.
>   - 규모가 작다. 1년이 지나도 수백 페이지 수준이라 grep으로 충분하다.
>   - 벡터 검색은 내용이 비슷한 `대체됨` 결정까지 함께 가져와서 옛 정책으로 답할 위험이 있다.
> - **도입을 검토할 신호**
>   - 검색 평가셋의 R@5가 기준에 못 미치고, 질의 정규화와 용어집 보강으로도 나아지지 않는다.
>   - `report_gap`에 "위키에 답이 있는데 단어가 달라 못 찾은 질문"이 자주 쌓인다.
>   - `raw/`가 많이 쌓여 "언제 논의했지?" 같은 원본 검색이 필요해진다.
>   - `index.md`가 너무 커져 한 번에 읽기 어려워진다.
> - **도입할 때 원칙**
>   - 검색 인터페이스(MCP를 도입했다면 `search_wiki`)는 그대로 두고 내부 구현만 바꾼다(grep → 키워드 + 임베딩 하이브리드).
>   - 별도 DB 서버는 두지 않는다. sqlite-vec이나 pgvector로 충분하다.
>   - 결정 상태를 메타데이터로 함께 저장하고, `대체됨` 결정은 검색 결과에서 걸러낸다.

## report_gap

답하지 못한 질문을 기록해 지식 공백 목록으로 만든다. 기록을 모을 곳(서버의 sqlite)이 필요해서 [MCP 서버](mcp-server.md#mcp-도구)와 함께 도입한다.
