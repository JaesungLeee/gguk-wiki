# 데이터 모델

위키에 무엇을 어떤 형식으로 저장하는지, 왜 그렇게 정했는지 적는다. 규칙과 형식의 정본은 [`AGENTS.md`](../AGENTS.md), [`procedures/`](../procedures/), [`templates/`](../templates/), [`domains.yml`](../domains.yml)이다. 저장 흐름은 [ingest.md](ingest.md), 조회 흐름은 [retrieval.md](retrieval.md)를 따른다.

## 진실의 기준 (Source of Truth)

규칙: [AGENTS.md 진실의 기준](../AGENTS.md#진실의-기준)

- 정책·의도의 기준을 가장 최근의 유효한 결정으로 둔다. 위키 페이지는 그 결정을 모아 보여 주는 목록일 뿐이다.
- 화면 디자인은 Figma가 기준이다. 화면 정의를 위키로 옮기면 Figma가 바뀔 때마다 위키가 낡는다. 위키에는 디자인 결정만 남긴다.
- 실제 동작은 코드가 기준이다. 정책과 구현이 어긋날 수 있으므로, 서로 다르면 어느 쪽도 자동으로 고치지 않고 표시만 한다.

## 위키 구조

규칙: [AGENTS.md 위키 구조](../AGENTS.md#위키-구조), [procedures/ingest.md 파일 이름](../procedures/ingest.md#파일-이름)

직무별이 아니라 도메인별로 나눈다. 한 페이지에서 서버/Android/iOS에 공통인 정책을 볼 수 있다. 플랫폼별 구현 위치는 위키에 적지 않고 조회할 때 코드에서 찾는다([코드 조회](retrieval.md#코드-조회)).

`scripts/`(인덱스 생성·형식 검사, `setup-workspace.sh`)는 [인덱스 생성과 형식 검사](ingest.md#인덱스-생성과-형식-검사)와 [작업 공간](plugin.md#작업-공간), `plugin/`은 [plugin.md](plugin.md)를 따른다.

**원본 자료 (`raw/`)**

- `raw/`의 파일은 넣은 뒤 고치지 않는다. 모든 결정의 `source`가 손대지 않은 원본을 가리키게 하기 위해서다.
- 기획 문서가 고쳐지면 기존 파일을 바꾸지 않고 새 파일로 다시 넣는다. 같은 이유다.
- 1단계는 마크다운만 받는다. 노션 페이지와 STT 요약도 마크다운으로 저장한다.
- 채팅 원본(`raw/notes/`) 형식은 [`templates/note.md`](../templates/note.md)다. 말한 사람을 `author`로 남겨 누가 언제 말했는지 기록한다.

**도메인 목록 고정**

규칙: [procedures/ingest.md 도메인](../procedures/ingest.md#도메인), 목록: [`domains.yml`](../domains.yml)

- 목록을 고정하는 이유는 `payment`, `payments`, `결제`처럼 같은 도메인이 여러 이름으로 갈라지는 것을 막기 위해서다.
- 목록은 `AGENTS.md`가 아니라 `domains.yml`에 둔다. 생성 스크립트와 형식 검사가 읽어야 하는데, 사람과 LLM이 읽는 마크다운 표는 파싱 형식이 흔들리기 때문이다. `AGENTS.md`의 표를 주석으로 감싸 파싱하는 안, 두 곳에 적고 CI로 일치를 검사하는 안도 검토했다.

도메인은 태그로만 쓴다. 도메인별 페이지(`wiki/domains/`)는 LLM이 고치지 않고 스크립트가 만든다([인덱스 생성과 형식 검사](ingest.md#인덱스-생성과-형식-검사)).

| 검토한 안 | 판단 |
| --- | --- |
| LLM이 도메인 페이지(정책 요약, 미결 목록)를 직접 고친다 | 제외. ingest PR마다 같은 페이지를 고쳐 merge 충돌이 반복된다. 요약이 결정 문서와 겹쳐, 대체된 결정이 요약에 남는 등 둘이 어긋난다 |
| **태그는 유지하고 페이지는 스크립트가 만든다** | 채택. 영역별로 묶어 보는 효과는 태그만으로 얻는다. 서술형 요약 대신 결정 목록이 된다 |
| 도메인을 없애고 grep만 쓴다 | 제외. "합류 시 푸시"처럼 본문에 "알림"이 없는 결정은 "알림"으로 찾을 수 없고, 영역 전체나 미결을 묻는 질문에 약하다 |

나누는 기준은 엔티티(방, 핀, 장소 등)를 기본으로 하고, 여러 엔티티에 걸친 흐름 2개(`onboarding`, `share-intake`)만 따로 둔다.

| 검토한 기준 | 판단 |
| --- | --- |
| 엔티티만 | 제외. "권한은 초반 진입 구간에서 요청"처럼 순서·시점에 관한 정책이 들어갈 곳이 없다 |
| 화면(PRD [000]~[007]) | 제외. 화면 구성은 자주 바뀌고(Figma 보드 번호도 바뀌었다), 방 이름 정책처럼 한 정책이 여러 화면에 걸친다 |
| **엔티티 + 흐름** | 채택. 정책이 걸리는 대상 단위로 묻는 경우가 많다. 경계가 애매하면 태그를 여러 개 단다 |

- 도메인 이름을 코드 모듈 이름에 맞출 필요는 없다. 코드 검색에는 도메인 이름이 아니라 용어집과 영어 직역을 쓴다.
- `design-system`을 둔다. 글자 크기 고정처럼 특정 화면·엔티티에 속하지 않는 디자인 결정이 들어갈 곳이 필요하다. 화면에 속한 디자인 결정(예: 지도 클러스터 표시)은 그 화면의 도메인에 넣는다. `platforms: [design]`만으로는 이런 결정이 어느 도메인 페이지에도 나오지 않는다.
- `auth`를 `user`와 나눈다. 인증·권한 결정과 프로필 규칙은 성격이 다르고, PRD도 인증을 별도 설계로 떼어 둔다.
- 결정과 미결 항목은 `domains`를 1개 이상 단다. 태그가 없으면 어떤 도메인 페이지에도 나오지 않아 조회 1단계에서 보이지 않는다.
- 도메인 이름을 바꾸거나 지울 때는 기존 결정 파일의 `domains`도 고친다. 결정 파일을 고치지 않는 이유는 결정 내용과 `source`를 지키기 위해서이고, 태그는 분류 정보이기 때문이다. 이름 변경을 금지하는 안, `domains.yml`에 별칭을 두는 안도 검토했다.

맞는 도메인이 없을 때는 새 도메인보다 기존 도메인의 `scope` 보강을 먼저 따진다. 목록을 만든 기준(엔티티 + 흐름)을 지키고, 기존 엔티티의 측면마다 도메인이 늘어나는 것을 막기 위해서다. 같은 영역의 결정이 2건 쌓이면 새 도메인을 만드는 안도 검토했다. 첫 결정이 그동안 다른 도메인 페이지에 걸려 있고, merge된 결정의 `domains`를 다시 고쳐야 해서 제외했다.

| 맞는 도메인이 없을 때 LLM이 할 일 | 판단 |
| --- | --- |
| 멈추고, 업로더가 `domains.yml` PR을 먼저 merge한 뒤 다시 ingest하게 한다 | 제외. 위키에 익숙하지 않은 팀원은 이 단계에서 막힌다. 확인은 후보로 받아도 같은 효과가 있다 |
| **후보로 보여 주고 업로더가 확인한 것만 넣는다** | 채택. 대체·미결 해소처럼 LLM은 후보만 내고 업로더가 정한다. 세션마다 이름을 짓지 않으므로 갈라지는 것을 막는다 |
| LLM이 직접 추가하고 PR에 표시한다 | 제외. 세션마다 LLM이 이름을 지으면 목록을 고정한 이유와 부딪힌다 |

| 도메인 변경을 넣는 PR | 판단 |
| --- | --- |
| `domains.yml` PR을 먼저 merge하고 ingest PR을 rebase한다 | 제외. 승인이 0명이라([승인 구조](ingest.md#승인-구조-ownership)) 따로 내도 검토 단계가 생기지 않는다. ingest PR을 먼저 열면 형식 검사가 실패하고, 다시 실행해도 처음 커밋으로 검사해 통과하지 않는다 |
| **ingest PR에 함께 넣고 확인 항목으로 PR 본문에 남긴다** | 채택. 형식 검사는 PR의 `domains.yml`로 검사하므로 바로 통과한다 |
| 함께 넣고 형식 검사가 `domains.yml` 변경을 경고로 표시한다 | 제외. 업로더가 PR을 만들기 전에 이미 확인하고, 검사에 경고 출력을 새로 만들어야 한다 |

- 후보를 보여 주기 전에 열린 PR을 찾는 이유는 merge 전의 도메인이 다른 세션에 보이지 않기 때문이다. ingest 스킬은 default 브랜치의 `domains.yml`을 주입한다([구성](plugin.md#구성)). 그 사이 다른 업로더가 `payments`를 만들 수 있다.
- 비슷한 도메인을 추가하는 PR이 있으면 그 PR이 merge된 뒤 이어 간다. 같은 항목을 두 PR에 넣으면 위치나 문구가 달라 충돌하거나 중복 검사에서 실패한다.

**플랫폼 내부 결정**

플랫폼 레포의 기술 결정(Android `docs/adr/` 등)은 위키에 옮기지 않는다. 각 레포에 이미 있고, 코드 조회 때 함께 찾을 수 있다. 옮기면 같은 내용이 두 곳에 생긴다.

다만 ADR 중 "무엇을 보여 주나"(동작, 화면 규칙, 플랫폼 간 계약)는 플랫폼 공통 결정이라 위키에 넣는다. "어떻게 구현하나"(모듈 구조, 라이브러리, 빌드, 개발 프로세스)만 넣지 않는다. 이렇게 나누지 않으면 플랫폼 간 불일치가 "플랫폼 내부 결정"으로 분류되어 위키에 들어오지 않는다. 2026-11-12에 Android ADR 46건을 확인했을 때 "무엇"이 들어 있는 것은 3건이었다(글자 크기 고정, 지도 클러스터, Firebase 익명 인증). 넣는 절차는 [ingest.md 입력](ingest.md#입력)을 따른다.

**용어집 (`wiki/glossary.md`)**

규칙: [procedures/ingest.md 용어집 반영](../procedures/ingest.md#용어집-반영)

조회할 때 기획 용어를 코드 심볼명으로 바꾸는 데 쓴다([질의 정규화](retrieval.md#질의-정규화)).

| 기획 용어 | 동의어 | Node | Android | iOS |
| --- | --- | --- | --- | --- |
| 보관함 | 저장 목록 | `SavedRoom` | `SavedRoom` | `Archive` |

- 직역으로 찾히는 용어(핀 → `pin`, 방 → `room`)는 적지 않는다. 세 플랫폼의 도메인 이름은 대부분 같은 영어 직역이므로, 직역이 아니거나 플랫폼마다 이름이 다른 용어만 적어 관리할 항목을 줄인다.
- 경로는 적지 않고 심볼명만 적는다. 파일을 옮겨도 고칠 필요가 없고, 이름이 바뀔 때만 고친다.
- 용어집은 도메인 페이지와 달리 손으로 고치는 파일로 둔다. 직역이 안 되는 용어가 나올 때만 고치므로 거의 모든 PR이 고치던 도메인 페이지보다 빈도가 훨씬 낮다. 표 끝에 추가하면 두 PR이 같은 위치를 고쳐 충돌하므로 가나다순 위치에 넣는다. 용어 1개를 파일 1개로 두고 표를 생성하는 안도 검토했다.
- 이름이 바뀌었을 때의 처리는 [코드 조회](retrieval.md#코드-조회)를 따른다.

## 공개 범위

규칙: [procedures/ingest.md 공개 범위](../procedures/ingest.md#공개-범위)

위키 레포는 public이다. 올라간 내용은 지워도 커밋 이력, fork, 검색 엔진 캐시에 남으므로 넣기 전에 거른다.

- 금지 항목이 있으면 PR을 만들지 않고 멈춘다. `raw/`는 고치지 않는 원본이므로, LLM이 지우지 않고 업로더가 원본에서 지운 뒤 다시 넣는다.
- 비밀값은 GitHub secret scanning도 검사한다. public 레포에서는 무료로 자동 실행된다.
- Figma 링크는 GGUK 디자인이 외부에 공개돼도 문제가 없어 허용한다.
- 레포에는 라이선스 파일을 두지 않는다. 공개는 하되 재사용 권리는 주지 않는다.

## 결정 문서 형식

형식: [`templates/decision.md`](../templates/decision.md), 규칙: [procedures/ingest.md 결정 대체](../procedures/ingest.md#결정-대체)

결정 1건을 파일 1개로 만들고, 상태와 대체 관계를 frontmatter에 기록한다. 이력이 있어야 "왜 바뀌었지?"라는 질문에 답할 수 있다.

- 승인 대기 상태(`proposed`)는 두지 않는다. GGUK에는 기획자나 따로 정한 결정권자가 없고 결정은 팀 합의로 정해지므로, 승인할 사람이 없다. 결론이 나지 않은 안건은 결정 문서가 아니라 미결로 둔다([미결 사항 형식](#미결-사항-형식)).
- 확정되지 않은 기획 문서는 넣지 않는다([기존 자료 이관](ingest.md#기존-자료-이관)).
- 대체 관계는 업로더가 확인한 것만 건다. 잘못 연결되면 유효한 결정이 검색에서 사라지기 때문이다.
- 값이 없는 선택 필드(`supersedes` 등)는 빈 값으로 두지 않고 줄을 뺀다. 형식 검사가 "필드가 있으면 값이 유효한가"만 보면 되고, 빈 값과 없음을 구분할 필요가 없다.
- 본문 다섯 섹션은 원본에 내용이 없어도 머리글을 두고 "원본에 없음"이라고 적는다. 원본에 없는 내용을 지어내지 않게 하면서 형식을 일정하게 유지하고, 나중에 회의록을 인용할 자리를 남긴다. 형식 검사는 frontmatter만 보고 본문은 업로더가 확인한다.

**유효 기간 구분 (`durability`)**

1단계에는 자동 오래됨 검사가 없다. 나중에 [주간 lint](backlog/automation.md#주간-lint)가 `temporal` 결정만 검사하도록 지금부터 기록해 둔다.

## 액션 아이템 형식

형식: [`templates/action-items.md`](../templates/action-items.md)

- 원본 1건의 액션 아이템을 파일 1개로 만들고, 경로는 원본의 `raw/` 아래 경로를 따른다. 회의록, 기획 문서, 채팅 원본의 이름이 같아도 겹치지 않게 하기 위해서다.
- `wiki/action-items.md`는 이 파일들로 스크립트가 만든다. 한 파일을 여러 ingest PR이 함께 고치면 merge 충돌이 반복되기 때문이다.
- 담당자는 원본에 적힌 이름 그대로 쓴다. 원본과 대조하기 쉽고, 이름과 GitHub 아이디를 잘못 짝지을 위험이 없다.
- 담당자는 선택 필드다. 회의에서 할 일만 정하고 담당자를 정하지 않는 경우가 있다. 필수로 두면 할 일이 기록에서 빠지거나 "미정" 같은 값이 이름처럼 섞인다.
- 완료는 다음 회의록과 채팅 두 경로로 반영한다([섹션별 반영 위치](ingest.md#섹션별-반영-위치)).

## 미결 사항 형식

형식: [`templates/open-questions.md`](../templates/open-questions.md)

회의에서 결론이 나지 않은 안건을 둔다. 액션 아이템과 같은 구조로, 원본 1건의 미결을 파일 1개(`wiki/open-questions/`)로 만든다.

- 도메인 페이지에 미결 목록을 손으로 적지 않는 이유는 [도메인 목록 고정](#위키-구조)과 같다.
- `domains`는 파일이 아니라 항목마다 단다. 회의 한 번에 여러 도메인의 미결이 나오고, 도메인 페이지는 항목을 도메인별로 모아야 하기 때문이다.
- `resolved`이면 `resolved_by`로 해소한 결정을 가리킨다. 어떤 결정으로 풀렸는지 남기고, 형식 검사가 그 파일이 있는 결정 문서인지 확인한다.
- 해소 연결은 대체 관계와 같이 업로더가 확인한 것만 건다.

| 검토한 안 | 판단 |
| --- | --- |
| **원본별 파일** | 채택. ingest 한 번에 파일 하나만 생기고, 액션 아이템과 형식·검사 코드를 함께 쓴다 |
| 미결 1건 = 파일 1개 | 제외. PRD 하나에서 작은 파일이 여러 개 생긴다 |
| 액션 아이템 파일에 합침 | 제외. 할 일과 정해지지 않은 것은 다른 개념이다 |

## 회의록 템플릿

형식: [`templates/meeting.md`](../templates/meeting.md)

템플릿은 권장 형식이다. 지키면 결정사항 추출 정확도가 높아진다. 형식이 자유로우면 "결정된 것"과 "논의만 한 것"을 헷갈리기 쉽다.

- 템플릿을 지키지 않은 회의록도 받는다. 과거 회의록처럼 다른 형식의 자료도 그대로 넣을 수 있어야 하고, `raw/`는 손대지 않은 원본이어야 하기 때문이다.
- 추출 오류는 업로더 확인 단계에서 거른다. 처리 방식은 [자유 형식 회의록 처리](ingest.md#자유-형식-회의록-처리)를 따른다.
- 노션에서는 frontmatter를 쓸 수 없으므로 `date`와 `attendees`를 페이지 속성으로 두고 섹션 제목만 맞춘다. 레포의 템플릿이 기준이고, 노션 템플릿과 조금 어긋나도 자유 형식 회의록으로 받으므로 영향이 작다.

**템플릿 위치**

템플릿은 레포 루트의 `templates/`에 둔다.

| 검토한 안 | 판단 |
| --- | --- |
| **`templates/` 폴더** | 채택. 형식 하나에 파일 하나라 기준이 한 곳이다. `wiki/` 밖이라 인덱스 생성·형식 검사 대상에 섞이지 않는다 |
| `AGENTS.md` 안에 넣음 | 제외. 매번 주입되는 규칙 파일이 길어지고, 사람이 회의록 템플릿을 복사해 가기 불편하다 |
| 플러그인 안에 넣음 | 제외. 플러그인을 업데이트해야 바뀌므로 팀원마다 다른 형식을 쓸 수 있다. 항상 `origin/HEAD`를 읽는다는 원칙과 맞지 않는다 |

상태 값의 의미도 템플릿 주석에 둔다. 상태 값은 형식의 일부라, 규칙 파일에 따로 적으면 값 목록과 의미가 두 곳에 나뉜다.
