# 기획서

- 작성일: 2026-11-27
- 작성자: Jaesung Lee

위키에서 공용 기획서를 뽑는 방식을 정한다([운영 방향](direction.md#위키-규칙에-남은-일) 1). 규칙은 [`procedures/proposal.md`](../procedures/proposal.md)가 정본이다.

## 독자와 쓰임

- 팀 전체(디자이너 포함)가 GitHub 레포의 Markdown으로 읽는다. 바뀐 부분은 갱신 PR 본문과 git diff로 본다.
- server와 iOS는 기획서를 그대로 읽는다.
- Android는 [sdd-android](https://github.com/JaesungLeee/sdd-android)로 PRD → spec → blueprint 버전 체인을 쓴다. 기획서가 그 체인의 PRD가 되어야 한다.

그래서 기획서는 sdd-android PRD와 아래를 맞춘다. Android의 spec은 PRD의 `revisions[].items`(항목별 등급)로 자신이 뒤처졌는지 판정하고, 항목 단위로 의존한다.

- frontmatter: `version`, `status: created`, `created`, `updated`, `revisions[].items`
- 항목 제목: `### [SCR-001] 이름`, 항목 범위(같은 수준 이상의 다음 제목 전까지)

## Android 연결

| 검토한 안 | 판단 |
| --- | --- |
| **sdd-android에 가져오기 명령을 추가한다** | 채택. 위키는 버전·개정 기록·항목 ID가 있는 기획서만 만들고, Android에서 명령이 위키 default 브랜치의 기획서를 받아 `docs/prd.md`와 해시를 쓴다. 위키가 sdd-android의 해시 형식과 CLI(Node)에 묶이지 않는다 |
| 위키가 sdd 형식의 완성본과 해시를 만들고 Android는 복사한다 | 제외. sdd-android는 고치지 않아도 되지만 위키가 sdd CLI를 쓰거나 해시 규칙을 똑같이 다시 구현해야 한다. CLI가 파일 이름을 `prd.md`로 고정한다 |
| sdd-android가 위키 clone의 기획서를 직접 읽는다 | 제외. 복사본이 없어 어긋나지 않지만 sdd-android를 크게 고쳐야 하고, Android 빌드와 CI가 위키 clone에 기대게 된다 |

- 가져오기는 1.0.0 이상만 받는다. sdd-android에는 0.x가 없다. 작성 중(`draft`)이면 버전이 없고, 완료하면 바로 1.0.0이다. 1.0.0이 개발 착수 시점이라는 [버전 규칙](#개정-등급)과 뜻이 맞는다.
- 처음 가져올 때 Android 체인을 새로 시작한다. Android의 기존 `docs/prd.md`(13.0.0) 이력은 잇지 않는다. 이어 가려면 가져오기가 Android의 기존 개정 기록을 합쳐야 하고, server와 iOS에는 뜻 없는 번호다.

## 위치와 이름

- 기획서는 `proposal/project-proposal.md`, 스킬은 `proposal`이다. 가져오기 명령이 Android에서 `docs/prd.md`로 써 주므로 위키 쪽 파일 이름은 sdd-android에 맞추지 않는다. 위키에서는 "PRD"라는 이름을 쓰지 않는다([이름](direction.md#문서별-역할)).
- 스킬 이름 `plan`은 제외했다. 폴더 이름과 다르고, Claude Code의 plan 모드와 헷갈린다.

## 변경 감지

| 검토한 안 | 판단 |
| --- | --- |
| **결정 단위로 대조한다** | 채택. 항목마다 근거 결정·미결을 기록하고, 갱신할 때 위키의 `decided` `product` 결정과 비교해 새 결정, 대체된 근거, 해소된 미결을 찾는다. 고칠 항목을 바로 알고 등급도 변화 종류로 제안할 수 있다 |
| 마지막으로 반영한 위키 커밋을 기록하고 git diff를 본다 | 제외. 단순하지만 바뀐 결정이 어느 항목에 들어가는지 매번 LLM이 추론해야 한다 |
| 매번 전체를 다시 쓰고 지난 버전과 비교한다 | 제외. 기준점이 필요 없지만 내용이 같아도 문장이 매번 달라져 `patch`가 쌓이고, 항목 ID가 흔들린다 |

대응표는 본문이 아니라 별도 파일(`proposal/sources.yml`)에 둔다. 본문이 기획 내용만 담고, Android로 가져간 본문에 위키 경로가 섞이지 않는다. 항목 근거 줄을 본문에 두는 안도 검토했다. 읽는 사람이 근거로 바로 가지만, 위키 경로가 개발 용어 없는 본문에 섞인다.

- frontmatter에는 기준점을 두지 않는다. sdd-android는 문서를 쓸 때 정해진 키만 다시 쓰고 나머지를 지운다(`src/core/frontmatter.ts`).
- 대응표가 대체된 결정을 가리키는 것은 오류가 아니라 경고다. ingest가 결정을 대체하면 대응표가 곧바로 낡는데, 이를 오류로 잡으면 ingest PR이 막혀 넣기와 기획서 갱신이 묶인다.

## 근거 범위

- `decided` `product` 결정만 본문의 근거다. `tech` 결정과 API 계약은 서버 API 명세와 각 파트 기술 문서의 몫이다([흐름](direction.md#흐름)).
- `open` `product` 미결은 `TBD:`가 된다. 지어낸 정책 대신 정해지지 않았다는 사실을 남긴다.
- 용어집의 기획 용어가 1장 용어가 된다. 결정의 심볼명은 용어집으로 바꾼다. 기획서는 개발 용어를 쓰지 않기 때문이다.
- 이관 기준선은 첫 기획서(1.0.0)의 1장 서술(배경, 한 줄 정의)에만 참고한다. 기준선은 `raw/`라 고치지 않으므로, 계속 근거로 쓰면 그 부분이 바뀌어도 대체로 잡히지 않는다. 기준선의 원칙과 목표는 이관 ingest가 결정으로 넣는다.

## 개정 등급

기준은 그 변경 때문에 다른 직군의 할 일이 어떻게 바뀌는지다.

| 등급 | 기준 |
| --- | --- |
| Major | 다른 직군이 이미 끝낸 작업을 다시 해야 한다 |
| Minor | 기존 작업은 유지되고 할 일만 늘어난다 |
| Patch | 할 일이 바뀌지 않는다 |

- 문서 버전과 항목 등급에 같은 기준을 쓴다. 이 기준은 sdd-android의 등급(MAJOR: 하위 문서를 다시 써야 함, MINOR: 늘어남, PATCH: 영향 없음), 하한(새 항목 MINOR 이상, 지운 항목 MAJOR), 버전 계산(가장 큰 등급 하나만 올림)과 같다. 그래서 sdd-android의 판정 로직을 고치지 않는다.
- 버전과 항목 등급을 두 층으로 나누는 안도 검토했다. 처음 검토한 기준에서는 누락 추가가 Patch였는데, 항목 등급도 Patch면 Android spec이 그대로 통과해 구현에 반영되지 않는다. 할 일 기준으로는 누락 추가가 Minor라 나눌 필요가 없어졌다.
- 정책 수치 변경(예: 만료 7일 → 14일)은 Major다. 디자인 문구와 구현을 다시 고쳐야 한다.
- 0.x는 초안 단계라 큰 변경도 Minor로 올린다. 첫 기획서는 MVP까지 구현된 기준선에서 뽑으므로 1.0.0부터 시작한다.
- 등급은 스킬이 근거와 함께 제안하고 실행한 사람이 승인한다.

## 본문

sdd-android PRD 템플릿(개요 / 목표·비목표 / 기능 명세 / 참고 자료)을 쓰고 위키에 맞게 고쳤다. Android의 sdd spec 단계가 읽는 구조(1장 용어, 2장과 3장의 ID 대응, Flow, `TBD:`)를 유지하기 위해서다.

- 제목을 "기획서"로 바꿨다.
- 「UI 용어」에는 상태 목록과 정책 수치만 둔다. sdd 템플릿은 "수치 기준"을 요구하지만 치수·색 값은 Figma가 기준이다([진실의 기준](data-model.md#진실의-기준-source-of-truth)).
- 3장 항목 묶음은 도메인이다. 위키와 같은 단위로 묶여 결정에서 항목을 찾기 쉽다.
- 4장 참고 자료에는 위키와 Figma 링크만 둔다. 출처는 대응표가 맡는다.

## 형식 검사

CI가 기획서와 대응표를 검사한다([형식 검사](ingest.md#인덱스-생성과-형식-검사)). Android가 가져간 뒤 sdd-android의 `check`가 낼 오류를 위키에서 먼저 잡는다.

- 형식: frontmatter와 개정 기록, 마지막 개정 = `version`, 버전 = 가장 큰 등급으로 올린 값(1.0.0부터), 2장과 3장의 ID 대응, 항목 중복
- 대응표: 근거 경로가 있는지, `tech` 결정을 가리키지 않는지, 이관 기준선은 `"*"`에만 있는지, 기획서에 없는 항목이 없는지, 버전이 같은지
- 손으로 고친 기획서: base와 본문이 다르면 개정 기록이 하나 늘고, 바뀐 항목마다 등급이 있어야 한다. 새 항목은 Minor 이상, 지운 항목은 Major다. sdd-android가 해시로 잡는 "미기록 변경"을 위키는 base 비교로 잡는다. 해시 파일을 따로 두지 않아도 된다
- 개발 용어: 본문(주석 제외)의 백틱
- 뒤처짐(경고만): 대응표에 없는 `decided` `product` 결정과 `open` `product` 미결, 대체된 근거, 모두 해소된 미결

뒤처짐을 오류로 막는 안은 제외했다. ingest PR마다 기획서 갱신까지 해야 해서 넣기가 무거워진다. 대신 ingest가 `product` 결정을 바꾸면 PR 본문에 갱신 안내를 남긴다.
